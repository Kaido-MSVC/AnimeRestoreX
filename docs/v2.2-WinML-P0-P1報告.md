## 2. 實作

### 2.1 版本與下載

- `tools/fetch-runtime.ps1`：預設 `-Flavor windowsml`，下載 `microsoft.windows.ai.machinelearning.2.5.96.nupkg`，SHA-256 `35d6e84f…09653a3`（與 v2.0 起固定的值相同）不符就刪檔並停止。
- 套件內的 DLL：

| 檔案 | 版本 | SHA-256 |
|---|---|---|
| `onnxruntime.dll` | 1.28.3.20261013.1.1b92d6e | `f4904f83…0538ef` |
| `DirectML.dll` | 1.15.4+241025-1615.1.dml-1.15.fac7597 | `82c6e345…2c0894` |
| `Microsoft.Windows.AI.MachineLearning.dll` | 2.5.96.5615 | `8205a572…7be0` |

- `DirectML.dll` 的檔案版本與上游 `Microsoft.AI.DirectML` 1.15.4 相同，但位元組不同（上游 `9c9e6d82…`），應該是另外簽章的版本。
- `dumpbin /dependents`：`onnxruntime.dll` 只依賴系統 DLL 與 `DirectML.dll`，**不依賴** `Microsoft.Windows.AI.MachineLearning.dll`；後者依賴 `onnxruntime.dll`。三者都不依賴 VC 執行階段。

### 2.2 CMake 與載入

- `ARX_ORT_FLAVOR` 預設 `windowsml`；windowsml 時找不到 2.5.96 就停止，`ARX_RUNTIME_DLLS` 多複製 `Microsoft.Windows.AI.MachineLearning.dll`。
- `initOrtRuntime` 依序載入 `DirectML.dll` → `onnxruntime.dll` → `Microsoft.Windows.AI.MachineLearning.dll`（`ARX_ORT_WINDOWSML` 時），沿用原本的做法：`SetDefaultDllDirectories`、絕對路徑 `LoadLibraryExW`、確認模組路徑與同名模組只有一份、`GetVersionString()` 必須是 1.28.3 才 `InitApi`。最後一個 DLL 只是固定位置，不呼叫它的任何函式，所以不會用到 `ExecutionProviderCatalog`，也不會下載 EP。
- `models/manifest.json` 只改 `runtime`（使用者同意）：flavor、套件與三個 DLL 的版本、雜湊。`models`、`pipeline`、`sources` 都沒動。
- 錯誤分類、取消、GPU 復原的程式碼沒有改。

### 2.3 EULA 同意畫面

- 從 `c2093f3` 的 `EulaDialog` 找回，參考 `docs/v2.0-P5/eula_*.png`。內容只放套件附的 `license.txt`（原樣嵌入 exe，英文原文），上方說明與按鈕有翻譯。
- 第一次啟動時，在寫入任何設定、載入 runtime DLL 之前顯示；「我同意」要先勾選才能按，預設按鈕是「我不同意」；不同意就結束程式。
- 同意後記錄 `v2/eula/windowsMlTerms` = 條款檔的 SHA-256。新的鍵，與 schema 2 會刪掉的舊鍵 `v2/eula/acceptedVersion` 不同；條款內容改變時會再詢問。
- 「關於」多一個「授權條款」按鈕（檢視模式），第三方元件改列 Windows ML Runtime 2.5.96（ONNX Runtime、DirectML 版本）。「授權與聲明」本來就列出 `licenses/` 的所有檔案，所以會出現 `WindowsML/license.txt`。
- upstream 建置沒有條款要同意（`EulaDialog::required()` 為 false，「關於」沒有這個按鈕）。
- 9 個新字串都有 zh_TW／ja 翻譯，兩個 .ts 都是 233 項、0 個 unfinished。lupdate 會掃描嵌入的 `license.txt` 並印出 4 個「Excess closing parenthesis」警告，不影響結果。

### 2.4 封裝與授權

- `tools/package.ps1` 依 manifest 的 `runtime.flavor` 封裝，建置時傳入同一個 `ARX_ORT_FLAVOR`，CMake cache 不符就停止。allowlist、雜湊與版本檢查的 DLL 清單取自 manifest。名稱與內容裡出現「Windows ML」「EULA」的檢查只留給 upstream；一種 runtime 的封裝不得帶另一種的授權資料夾。依賴檢查多擋 `Microsoft.Windows.AI.*` 來自 System32 的情況。
- `tools/collect-licenses.ps1 -Flavor`（預設 windowsml）：`licenses/WindowsML/license.txt`（`66395f8c…`）與 `ThirdPartyNotices.txt`（`fb0af774…`）從套件原樣複製，刪除 `ONNXRuntime/`、`DirectML/`。Qt 與 nunif 的檔案沒有變更。WinML 的 `ThirdPartyNotices.txt` 與原本的 `ONNXRuntime/ThirdPartyNotices.txt` 內容相同（git 記成改名）。

## 3. P0：probe（`tools/winml-probe`，`build\` = Windows ML 套件建置）

結果都在 `tools/winml-probe/_work/v22p0/`。probe 以 `-Runtime winml -Clean` 重新建置，`--runtime-dir` 指向 `third_party\windowsml\2.5.96\runtimes\win-x64\native`，`--expect-ort 1.28.3`。

### 3.1 初始化與 session

`run-p1redo.ps1 -Stage load -ModelsRoot third_party\models`（主程式實際用的 14 個模型）：DML 與 CPU 都能建立 session（exit 0）。節點分配與 1.24.4 相同：v3 1× DML 968／CPU 81、2× 970／81，`IsNaN`、`Resize`、`Pad` 都在 DML；舊 4× 圖 DML 1996／CPU 1091。

### 3.2 是否還需要模型改寫（`run-v22p0.ps1`）

tile 256，PyTorch 參考沿用 `_work/p1redo/t256`（torch 2.14.1+cpu）。

| 圖 | 原始匯出檔 | 只做 rewrite_pad | rewrite_pad + fix_reshape_allowzero |
|---|---|---|---|
| v3 noise3（1×） | DML：Reshape 失敗（`node_Reshape_3225`，8007023E）；CPU 最多差 1 | DML：同樣失敗 | DML 最多差 1，142.01 dB |
| v3 noise2_scale2x | DML：Reshape 失敗；CPU 最多差 1 | DML：失敗 | DML 最多差 1，140.71 dB |
| v3 scale2x | DML：Reshape 失敗；CPU 最多差 1 | DML：失敗 | DML 最多差 1，143.72 dB |
| 舊 4× scale4x | DML 能跑但**輸出錯誤**（1.77 dB，最多差 255）；CPU 最多差 1 | DML 最多差 1，133.55 dB | 同左（allowzero 這一步對舊圖是 no-op，檔案相同） |
| 舊 4× noise3_scale4x | DML 輸出錯誤（2.84 dB）；CPU 最多差 1 | DML 最多差 1，135.77 dB | 同左 |

另外 `-Stage rawpad`（只做 allowzero、不做 rewrite_pad）：v3 noise3 在 DML 上能跑但輸出錯誤（1.70 dB），所以 v3 的負數 Pad 改寫也還需要。

**結論**：ORT 1.28.3（Windows ML 2.5.96）與 1.24.4 一樣，DML 的負數 Pad 仍輸出錯誤、`Reshape allowzero=1` + `-1` 仍失敗，兩步改寫都還需要。目前的模型與流程不用調整。

### 3.3 改寫後對 PyTorch

- tile 256：見上表最右欄，全部 8 位元最多差 1。
- `-Stage tile`，v3 noise3 與 noise2_scale2x 在 DML：160（142.42／140.11 dB）、256（142.01／140.71）、352（142.05／140.67）、448（141.92／140.64），全部最多差 1，與 1.24.4 的結果同等。

### 3.4 取消（probe）

`-Stage cancel`，DML 的 `SetTerminate()`：

| 模型 | tile | 延遲 | 結果 |
|---|---|---|---|
| v3 noise2_scale2x | 448 | 50 ms | 中止，SetTerminate 後 10.6 ms |
| v3 noise2_scale2x | 448 | 150 ms | **沒有中止，Run 跑完**（SetTerminate 後 334.5 ms） |
| swin_unet/art noise3_scale4x | 256 | 50 ms | 中止，0.3 ms |
| swin_unet/art noise3_scale4x | 256 | 150 ms | 中止，0.2 ms |

與 v2.0 P1 重做相同：DML 上的 `SetTerminate()` 不可靠，維持「DML 在 tile 之間取消」的決策。取消後再 Run 都正常，輸出與第一次相同。主程式的取消延遲見 §4.4。

### 4.3 GPU 復原（照 v2.0 交接 §7）

v3 noise2_scale2x，PNG，`01_sakura_portrait`、`02_sunset_boy`、`06_chibi_transparent`。

| 情境 | 第一次錯誤 | 結果 |
|---|---|---|
| 真實 OOM（`forced`，`--force-oom-tile 1600`） | **887A0007**（DEVICE_RESET，歸類 DeviceLost） | 3 張成功；第 1 張重建後 160（`oom_retry`，45.3 s），其餘沿用 160（`after_gpu_error`）；重建時 session 數 0；對 `ref160` 最大差 0；釋放後 284.3 MiB |
| 同上重跑 2 次（`forced2`、`forced3`） | 8007000E | 同上，對 `ref160` 最大差 0；第 1 張 11.7 s／10.0 s |
| 真實 DeviceLost（`dlreal`，加 `--force-device-lost`） | 8007000E → 887A0006 | 2 張成功，對 `ref160` 最大差 0 |
| 同程序兩個 job（`twice`） | 8007000E | 兩次都復原成功，釋放後 293.9／295.3 MiB，沒有累積 |
| 模擬重建失敗（`failrebuild`） | 8007000E → 887A0006 | 第 1 張失敗、fatal，未處理 2，沒有輸出；訊息含錯誤碼 |
| 模擬重做失敗（`failredo`） | 8007000E → 8007000E | 同上 |
| 手動 160（`ref160`） | 無 | 對 v2.0 的 `p2oom/ref160` 最大差 0 |

**錯誤碼**：v2.0 第一次錯誤都是 8007000E；這次 3 次中有 1 次是 887A0007（v2.0 沒有出現過）。887A0007 本來就在 DeviceLost 的清單內，流程照常復原，不需要改程式。錯誤訊息仍帶 HRESULT（`MLOperatorAuthorImpl.cpp(2623)` … `80070…`），HRESULT 判斷方式有效。v2.0 交接 §4 已記錄實機 OOM 後錯誤碼不固定，這次是同一現象。
