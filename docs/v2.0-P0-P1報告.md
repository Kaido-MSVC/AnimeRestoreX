### 6.4 根因與最小重現（實測）

1. **圖最佳化等級**：`--opt disable/basic/extended` 三種的 noise3 在 DML 上都還是 1.70 dB、全為 0，所以不是 ORT 圖融合造成的。

3. **最小重現**（`scripts/make_pad_repro.py`，opset 17，輸入 `[1,3,256,256]`）：

## 8. 上游 tile、padding、alpha 規格（給 C++ 照著做）

來源：nunif `31c0137dc949807e382d918dc325c65fd6703092`（swin_unet/art 匯出當時）；到 master `0d3d92c` 只有格式化差異。

- `nunif/utils/seam_blending.py`：`SeamBlending.create_config`、`create_blend_filter`、`update`、`tiled_render`
- `waifu2x/models/swin_unet.py`：`tile_size_validator`、`SwinUNet*` 的 scale／offset／blend_size
- `waifu2x/utils.py`：`Waifu2x.convert`、`load_model`（alpha 的流程）
- `nunif/utils/alpha.py`：`AlphaBorderPadding`；`nunif/models/onnx_helper_models.py`：ONNX 版
- `nunif/transforms/functional.py`：`quantize256`
- 對照：`waifu2x/unlimited_waifu2x/public_html/script.js`（Web 版，直接使用同一批 ONNX）

### 8.1 模型參數

| 倍率 s | offset（輸出像素） | blend_size b（輸出像素） | input_offset = ⌈offset/s⌉ | input_blend = ⌈b/s⌉ |
|---|---|---|---|---|
| 1 | 8 | 4 | 8 | 4 |
| 2 | 16 | 8 | 8 | 4 |
| 4 | 32 | 16 | 8 | 4 |

合法 tile T（輸入邊長）：`T > 16 && (T−16) % 12 == 0 && (T−16) % 16 == 0`，也就是 `(T−16) % 48 == 0`：64、112、160、208、256、304、352、400、…。上游的 `find_valid_tile_size` 是從要求值往下找第一個合法值；預設 tile 256、batch 4。

### 8.2 計畫（輸入影像 H×W）

```
step_in  = T − (2·input_offset + input_blend)        // 三種倍率都是 T − 20
h_blocks = 最小的 n，使得 (n−1)·step_in + T ≥ H + 2·input_offset   // 上游用 while 迴圈：
           input_h = 0; n = 0; while (input_h < H + 2·input_offset) { input_h = n·step_in + T; ++n; }
w_blocks、input_w 同理
pad = (left = input_offset, right = input_w − (W + input_offset),
       top  = input_offset, bottom = input_h − (H + input_offset))
step_out = step_in · s
緩衝區大小 = (input_h · s) × (input_w · s)，最後輸出 = 左上 (H·s) × (W·s)
```

- padding 模式：**replicate**（`F.pad(..., mode='replicate')`；Web 版 art 也是 "replication"）。右／下的 pad 可能大於 input_offset，因為要補到整數個 tile。
- tile (h_i, w_i) 的輸入：padded 影像 `[h_i·step_in, h_i·step_in + T) × [w_i·step_in, …)`。
- 模型輸出邊長 `T·s − 2·offset`，直接放在緩衝區 `[h_i·step_out, h_i·step_out + T·s − 2·offset)`。因為 swin 的 `offset % s == 0`（input_offset·s == offset），這個座標就是原圖的輸出座標，不需要再平移。
- 相鄰 tile 的輸出重疊寬度 = `input_blend·s` = b（4／8／16），剛好等於融合帶寬。

### 8.3 融合權重

```
Ho = T·s − 2·offset
filter：中心 (Ho−2b)×(Ho−2b) 為 1；由內往外第 k 圈（k = 0..b−1）的值 = 1 − (k+1)/(b+1)
        （最外圈 = 1/(b+1)；每個 tile 的四邊都一樣，包括影像邊緣的 tile）
累加：每個像素 out = Σ(y_t · f_t) / Σ f_t
      上游的寫法是累進式：pixels = pixels·(W/(W+f)) + y·(f/(W+f))；W += f
最後：clamp(0, 1)，再裁到 (H·s)×(W·s)
```

- 上游在 float32 上累加；Python CLI 用 `i2i_blend_size`（4／8／16）。**Web 版固定使用 `BLEND_SIZE = 16`**，和 CLI 不同，C++ 以 CLI 為準。
- 量化（`quantize256`）：`uint8(clamp((x + 0.5/255·(1 − 1e−7))·255, 0, 255))`，等於向下取整加近 0.5 的四捨五入。Web 版用 `x·255 + 0.49999`。
- Web 版另有 "color_stability"：單色 tile 跳過推論（art 預設開）。CLI 沒有，屬於可選最佳化。
- 記憶體：上游為整張輸出保留 float32 的 pixels 與 weights（各 3×緩衝區大小）。75 MP 時約 0.9 GB×2，P2 要評估條帶化（規劃 §8.3）。

### 8.4 Alpha（`Waifu2x.convert`）

1. RGBA 拆成 RGB（3×H×W，0–1）與 alpha（1×H×W，0–1）。alpha 全為 1 時視同沒有 alpha（`blank_alpha`）。
2. 有 alpha 且不是全 1：先對 RGB 做 **alpha border padding**，迭代次數 = 該模型的 offset（1× 8、2× 16、4× 32，單位是輸入像素次數）：
   ```
   mask = (alpha > 0)；RGB[mask == 0] = 0
   重複 offset 次：
     w = 3×3 box sum(mask)（zero padding）
     b = 3×3 box sum(RGB)（每個通道分開）/ (w + 1e−7)
     RGB[mask == 0] = b[mask == 0]
     mask = (w > 0)
   RGB = clamp(RGB, 0, 1)
   ```
   也就是把不透明區的顏色往透明區擴散 offset 圈，避免透明區的 RGB 滲入邊緣。是 straight alpha，**沒有** premultiply。
3. RGB 用選定的模型做上面的 tiled render。
4. alpha 的處理：
   - noise（1×）：alpha **原樣保留**（Web 版用 `scale1x.onnx`，一個只裁 offset 的旁路模型，效果相同）。
   - scale／noise_scale（2×）：alpha 複製成 3 通道，用 **`scale2x`（不降噪）**做 tiled render，再取 3 通道平均。沒有 scale2x 模型時用 bilinear。
   - scale4x／noise_scale4x：同上，改用 **`scale4x`**。
   - alpha 全為 1：用 nearest 放大。
5. 輸出 RGBA 時，RGB 與 alpha 分別量化。alpha 的 tile 計畫與 RGB 相同。

### 12.2 改寫工具與規則

- `tools/winml-probe/scripts/rewrite_pad.py`（SHA-256 `edcd94f5853e0cad07c7de9a672f357b243dfd3bc750e449fb8272ee6fd0875f`），只在開發期使用，不隨正式包發行。逐一檢查每個 Pad 節點：
  - `mode` 不是 constant，或有 `axes` 輸入：**STOP**（exit 2，不寫出檔案）。
  - pads 只由 initializer 或 Constant 算出：用 `onnx.reference` **精確求值**。全 ≤ 0 就換成等價的 Slice；正負混合就拆成 Slice＋Pad；全 ≥ 0 就不動。
  - pads 是動態的（依賴輸入 shape）：用保守的區間分析算出每個元素的上下界。下界 ≥ 0 代表不會裁切，不需要改寫，保留不動；否則 **STOP**。
  - 權重與其他節點都不動。被替換節點原本計算 pads 的子圖留在圖中，不再被使用（ORT 載入時會移除）。
- 14 個 attention Pad 的 pads 是 `(6 − H mod 6) mod 6`（Python 式 Mod，除數 6），區間分析得出 [0, 5]，因此保留不動（你已同意這個超出原指示的處理）。`/unet/Pad` 是常數子圖，精確求值為 `[0,0,−6,−6,0,0,−6,−6]`，換成 `Slice(starts=[6,6], ends=[−6,−6], axes=[2,3], steps=[1,1])`。
- 自我測試 `scripts/test_rewrite_pad.py`：5/5 通過。常數負值、Cast 算出的負值、正負混合加非 0 constant_value 這三種改寫後，CPU 都逐位元相同；reflect mode 與可能為負的動態 pads 都正確 STOP。
- 重現性：用最終版腳本重新改寫 14 個模型，輸出與第一次逐位元相同。
- 草稿 `models/manifest.json`：由 `scripts/make_manifest.py` 從每個模型的改寫報告產生。內容包括來源 zip 與 commit、原始與改寫後的 SHA-256、工具版本、I/O 契約（offset、blend_size、合法 tile 規則、replicate padding）與 alpha 用的模型。授權欄標為 `UNRESOLVED`，狀態標為 DRAFT（不可發布）。

#### 887A0006（觀察結果）

- noise3_scale4x、tile 640、正常推論（不是診斷模式）、第一個程序：建立 Session 2,354 ms，**第一次 Run 7,317 ms 並成功回傳**，輸出形狀正確。接下來的第一次暖機 Run 回傳 `DML GPU readback failed with HRESULT 0x887A0006`（DXGI_ERROR_DEVICE_HUNG），在 `DmlCommandRecorder.cpp(371)` 回報。
- 依停止條件，在這裡停止了所有 GPU 測試：沒有縮小 tile 重試，也沒有在同一個 Session 上重試。noise3 的 640 與其他 640 組合**未執行**。
- 同一時段的 System log **沒有 Display 4101**，也沒有 Display、dxgkrnl、nvlddmkm 的事件。`LiveKernelReports` **未執行**。事後 `nvidia-smi` 顯示 GPU 正常（使用 555 MiB，50°C）。
- **推論（未證實）：VRAM 超用。** 依據：(1) 同一個模型在 400 用了 2,802 MiB；按 tile 面積比 (640/400)² ≈ 2.56 推算約 7.2 GB，超過這張卡的 6,029 MiB。另外 scale2x 實測 400→640 的 VRAM 比是 3,357／1,392 ≈ 2.41，按這個比例推算約 6.75 GB，同樣超過。(2) 第一次 Run 需要 7.3 s，而 400 時只要 1.1–1.4 s，符合記憶體不足時退到共用記憶體的現象。沒有做 VRAM 或驅動層的直接量測，所以這只是推論，不是已證實的原因。

#### 建議的 tile 政策

| 設定 | 建議 | 理由 |
|---|---|---|
| Auto 預設 | **256** | 三個模型 VRAM 都 ≤ 920 MiB、單 tile 0.18–0.25 s；400 的吞吐量只多 2–9%，VRAM 卻是 1.5–3 倍（4× 模型 2.8 GB） |
| OOM 或裝置錯誤後縮小 | **160** | 縮小一階到合法尺寸。160 的速度與記憶體**未實測**，P2 要補量 |
| 手動 | 400 | 6 GB 卡上實測可用；4× 模型要 2.8 GB VRAM |
| 不提供 | ≥ 640 | 4× 模型在 6 GB 卡上裝置停止回應 |

### 12.8 取消政策

| 路徑 | 機制 | 預期延遲（依 §12.7 實測，暖機後單 tile） |
|---|---|---|
| DML | **只在 tile 之間生效**。§6.6 已實測 `SetTerminate()` 不會中斷正在執行的 DML Run，所以最壞情況要等目前這個 tile 做完 | 256：1×／2× 約 0.18–0.20 s、4× 約 0.22–0.26 s。400：1×／2× 約 0.48 s、4× 約 0.55–0.60 s。第一個 tile 包含冷啟動，再加約 0.7–1.4 s |
| CPU | tile 之間檢查，Run 中另外呼叫 `RunOptions::SetTerminate()` | §6.6 實測 1–3 ms 內中止；之後 `UnsetTerminate()` 就能繼續使用同一個 Session |

### 12.9 scale1x.onnx 棄用

`scale1x.onnx` 本身就是一個 `Pad(−8)`，在 DML 上會輸出全 0。1× 無降噪本來就不處理；alpha 或其他需要扣掉 offset 的地方，一律在 C++ 中直接裁切（1× 時 alpha 原樣保留，§8.4）。manifest 也記錄為不使用。

### 12.10 P3 工項（新增）

1. **TileProcessor 在 Run 之前拒絕非法尺寸，直接報錯。** 只允許 `T > 16 && (T − 16) % 48 == 0`。原因：上游 PyTorch 的尺寸斷言（`tile_size_validator`）不會進入 ONNX 模型。§12.6 實測顯示，非法尺寸有的會報錯（250 在 `/unet/Add` 形狀不符），有的會**靜默執行**（100、128、200、300、512 的 attention window padding 不為 0，輸出形狀看起來正常，但結果與上游的切法不同）。不能靠 ORT 報錯來攔截。
2. **依預算選擇 tile，不寫死。** 用 DXGI `QueryVideoMemoryInfo` 的 Budget／CurrentUsage，配合 §12.7 實測的每個 tile 尺寸與倍率的 VRAM 表選擇 tile。表中沒有的組合（例如 160）不推測，要先實測。
3. **DXGI 裝置錯誤一律歸類為「引擎不可信」：** `DXGI_ERROR_DEVICE_HUNG`（887A0006）、`DEVICE_REMOVED`（887A0005）、`DEVICE_RESET`（887A0007）、`DRIVER_INTERNAL_ERROR`（887A0020）。處理方式：停止目前的項目、釋放 Session、重建裝置，之後依規劃 §10.3「裝置遺失／Session 不可信」決定批次是否繼續。**不得**把它當成 OOM 用縮小 tile 重試，也**不得**在原本的 Session 上靜默重試。判斷要用 HRESULT 數值，不要比對英文訊息字串（規劃 §10.3）。
4. DML 的取消只在 tile 之間檢查；CPU 路徑另外在 Run 中呼叫 `SetTerminate`（§12.8）。
5. 正式程式不使用 `ep.dml.*` 這類未公開設定。

### 12.11 上游 issue 草稿（microsoft/onnxruntime，只草擬，未送出）

tile 300 附帶測試在 DML 上沒有出錯，所以 issue 不需要補充附帶發現。最小重現的腳本就是現有的 `scripts/make_pad_repro.py`。

> **Title:** [DirectML EP] `Pad` with negative pads (cropping) returns all zeros
>
> **Describe the issue**
>
> With the DirectML execution provider, an ONNX `Pad` node (mode `constant`) whose `pads` contain negative values returns a tensor of the correct (cropped) shape filled with zeros. The CPU EP returns the expected cropped data. ONNX defines negative pads as removing elements, so the expected output equals the equivalent `Slice`. Session creation and `Run` both succeed, and no error or warning is reported. The node is not assigned to the CPU EP either.
>
> PyTorch emits this pattern for `F.pad(x, (-6, -6, -6, -6))`. We found it in the waifu2x `swin_unet` ONNX models (nagadomi/nunif), where every output from the DirectML EP is wrong (PSNR ≈ 2–4 dB, and one model returns all zeros).
>
> | Model (input `[1,3,256,256]` float32, opset 17) | DirectML EP | CPU EP |
> |---|---|---|
> | `Pad(x, pads=[0,0,-6,-6,0,0,-6,-6])`, pads as initializer | **all zeros**, shape `[1,3,244,244]` | correct |
> | same, pads computed by `Cast(float initializer)` | **all zeros** | correct |
> | equivalent `Slice(starts=[6,6], ends=[-6,-6], axes=[2,3])` | correct | correct |
> | positive `Pad(pads=[0,0,6,6,0,0,6,6])` | correct | correct |
>
> In the full swin_unet model, the graph optimization level does not matter: `ORT_DISABLE_ALL`, `BASIC`, `EXTENDED` and `ALL` all give zeros. With package 2.4.89 (ORT 1.27.1), only the first and third rows were run, with the same results.
>
> **To reproduce**
>
> ```python
> # make_pad_repro.py - writes pad_neg_const.onnx (opset 17, IR 8)
> import numpy as np, onnx
> from onnx import TensorProto, helper, numpy_helper
> x = helper.make_tensor_value_info("x", TensorProto.FLOAT, [1, 3, 256, 256])
> y = helper.make_tensor_value_info("y", TensorProto.FLOAT, [1, 3, 244, 244])
> pads = numpy_helper.from_array(np.array([0, 0, -6, -6, 0, 0, -6, -6], np.int64), "pads")
> g = helper.make_graph([helper.make_node("Pad", ["x", "pads"], ["y"], mode="constant")],
>                       "pad_neg", [x], [y], [pads])
> m = helper.make_model(g, opset_imports=[helper.make_opsetid("", 17)], ir_version=8)
> onnx.checker.check_model(m)
> onnx.save(m, "pad_neg_const.onnx")
> ```
>
> Then run it with the DML EP (C++ shown; the session settings follow the DirectML EP docs):
>
> ```cpp
> Ort::SessionOptions so;
> so.DisableMemPattern();
> so.SetExecutionMode(ExecutionMode::ORT_SEQUENTIAL);
> const OrtDmlApi* dml = nullptr;
> Ort::ThrowOnError(Ort::GetApi().GetExecutionProviderApi("DML", ORT_API_VERSION,
>                                                         reinterpret_cast<const void**>(&dml)));
> Ort::ThrowOnError(dml->SessionOptionsAppendExecutionProvider_DML(so, 0));
> Ort::Session s(env, L"pad_neg_const.onnx", so);
> // input: any non-zero [1,3,256,256] tensor
> // expected: y == x[:, :, 6:250, 6:250]; actual: y is all 0.0f
> ```
>
> **Expected behavior:** `y` equals `x[:, :, 6:-6, 6:-6]`, as with the CPU EP and the equivalent `Slice`.
>
> **Urgency:** Not urgent for us. We work around it by rewriting negative constant `Pad` nodes into `Slice` offline, but the failure is silent and produces wrong results.
>
> **Platform / versions**
>
> - OS: Windows 11 25H2, build 26200.9711, x64
> - ONNX Runtime: 1.28.3 as shipped in the NuGet package `Microsoft.Windows.AI.MachineLearning` 2.5.96 (`onnxruntime.dll` 1.28.3.20261013.1.1b92d6e). Also reproduced with package 2.4.89 (ORT 1.27.1).
> - DirectML: `DirectML.dll` 1.15.4 (1.15.4+241025-1615.1.dml-1.15.fac7597), loaded from the application directory
> - Execution provider: DirectML (`OrtDmlApi::SessionOptionsAppendExecutionProvider_DML`, device 0)
> - GPU: NVIDIA GeForce GTX 1060 6GB, driver 32.0.15.8180
> - Language / API: C++ (`onnxruntime_cxx_api.h` from the package)
> - Model: opset 17, IR 8, FP32
>
> Not tested: other GPUs or vendors, other DirectML versions (e.g. the 1.15.x redistributable from NuGet `Microsoft.AI.DirectML`), and the Python `onnxruntime-directml` package.
