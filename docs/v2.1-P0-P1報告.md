## 3. P0：只改標準

### 3.1 /std 旗標

| 階段 | debug | release |
|---|---|---|
| 只改成 `CMAKE_CXX_STANDARD 23` | `-std:c++latest` ×50 | `-std:c++latest` ×50 |
| 加上對應設定後 | `-std:c++23` ×50，沒有 `c++latest` | `-std:c++23` ×50，沒有 `c++latest` |

- **原因**：CMake 4.4.4 的 `Modules/Compiler/MSVC-CXX.cmake` 第 45–49 行，只要 MSVC ≥ 19.29.30129，就把 C++23 一律對應到 `-std:c++latest`。
- **cl 19.52 實測**：`/std:c++23` 可以用，`__cplusplus` 為 202302L；`/std:c++latest` 是 202400L；`/std:c++23preview` 會出 D9048（已棄用）。兩種模式都有 `__cpp_lib_expected`、`__cpp_lib_mdspan`、`__cpp_lib_flat_map`，都沒有 `__cpp_lib_submdspan`。
- **做法**（使用者決定）：在 `project()` 之後加入下面這段，`CMAKE_CXX_STANDARD 23` 保持不變；其他編譯器維持 CMake 預設。註解寫明 CMake 原生支援 `-std:c++23` 之後就移除。

```cmake
if(MSVC AND CMAKE_CXX_COMPILER_VERSION VERSION_GREATER_EQUAL 19.52)
    set(CMAKE_CXX23_STANDARD_COMPILE_OPTION "-std:c++23")
    set(CMAKE_CXX23_EXTENSION_COMPILE_OPTION "-std:c++23")
endif()
```

### 3.2 一起修的建置問題

- **`build.ps1`**：`-vcvars_ver` 由 14.51 改成 14.52。14.51 已經不在這台電腦上，原本的腳本無法進入開發環境。
- **CMake 快取**：`build/debug` 的快取還記著 14.51 的 `link.exe`，所以用 `cmake --preset debug --fresh` 重新設定過；release 用 `build.ps1 -Clean` 重建。
- **`tools/winml-probe`**：同樣的 C++23 對應寫在 `CMakeLists.txt`，整個 probe 專案改成 23（`tile_runner` 會直接編譯 `src/core/inference/`）。probe 的 `build.ps1` 也寫死 14.51，一起改成 14.52，否則無法建置。README 中兩處「C++20」改成 C++23。
- **probe 驗證**：`build.ps1 -Clean` 後 `build.ninja` 有 13 處 `-std:c++23`，`tile_runner` 用目前的 `models/manifest.json` 跑 v3 noise2_scale2x、DML、tile 256，exit 0，`sha256_verified: true`。P0 只要求能建置和執行，沒有重跑完整的 probe 驗證。
  - 舊的 `_work/p1redo/image/manifest-v3.json` 是加入 `tile_rule` 之前的格式，現在的程式會拒絕它。這與 C++23 無關。

### 3.3 編譯問題

C++23 下沒有編譯錯誤，`/W4` 也沒有新警告。debug 與 release 都完整重建過，兩邊都只有 §2 那個既有的 C4456，所以 P0 沒有改任何原始碼。

### 3.4 驗證

- **arx_verify**：15 張全部最大差 0（§5）。
- **時間**：基準與 P0 交錯執行，基準 20.00／19.61／19.76 s，P0 19.81／19.77／19.75 s；2400×1606 的輸出最大差 0。

## 4. P1：推論核心改用 C++23 寫法

### 4.1 各項判定

| 項目 | 判定 | 理由 |
|---|---|---|
| `std::expected`：`makeTilePlan`、`upscaleImage` | **採用** | 回傳 `expected<TilePlan, Status>`、`expected<Image8, Status>`。出錯時根本沒有圖或計畫，「沒有部分結果」由型別保證，不再靠 `out.clear()`。`ProcessStats` 維持 out 參數，因為失敗時也要回報（第一次錯誤、attempts） |
| `std::expected`：`sha256File`、`resolveVerified` | **採用** | 同樣的模式：結果是雜湊字串、驗證過的路徑 |
| `std::expected`：`ModelContract::load` | 跳過 | 呼叫端（`EngineHost`、`tst_pipeline`）要長期保存 `loadStatus` 與 contract 兩者，改了只會在呼叫端再拆回兩個變數 |
| `std::expected`：`Backend::acquire`、`OrtTileEngine::create`、`ITileEngine::run` | 跳過 | `run` 的輸出 vector 會在 tile 之間重複使用（避免每個 tile 重新配置），改成回傳值會失去這個效果。`acquire` 是虛擬介面，tests 與 `arx_verify` 的 fake 都要跟著改，安全性也沒有提升（失敗時本來就把 engine 設成 nullptr） |
| `std::mdspan` | **採用**（熱點只用來算列起點） | RGB 平面、tile 輸入與輸出（[1,3,T,T] 省略 batch 1，通道數是靜態的 3）、累加器、權重、濾波器、alpha 平面都改用多維下標，取代手寫的 `c*n + y*w + x`。熱點迴圈逐元素用三維下標時，CPU 微基準慢約 5%（§6.2），所以 tile 擷取與融合累加只用 mdspan 算出列起點（`&in[c, sy, 0]`），最內層仍用指標，與原寫法相差在 1% 內 |
| `views::cartesian_product` | **採用** | tile 的兩層迴圈合併成一層，維持 row-major 順序（wi 變化最快）。浮點累加的順序會影響結果，所以加了註解 |
| `views::enumerate`／`zip` | 跳過 | 熱點迴圈都要用算出來的索引同時存取多個平面，沒有適合的地方；通道迴圈 `for c in 0..3` 改用 view 也不會更清楚 |
| `std::byteswap`：`Sha256.cpp` | 跳過 | 沒有大端序轉換：雜湊由 Windows CNG（`BCryptHashData`）計算，程式只把 32 位元組轉成十六進位。這部分改用 `std::format_to` 取代 `snprintf` |
| `std::flat_map`：`ModelContract` | 跳過 | 只有 14 個模型；`models()` 要保持 manifest 順序，要用 flat_map 就得另外維護一份索引。查詢改用 `std::ranges::find`（以 `&ModelInfo::id` 為投影） |
| `std::to_underlying` | 跳過 | core 裡沒有 enum 與整數互轉：裝置設定存成字串 `"cpu"`／`"gpu"`。整數轉換只在 UI（下拉選單資料），本輪不改 UI |
| `std::unreachable`：`errorKindName` 等 switch | 跳過 | switch 之後的 `return "?"` 是超出範圍值的安全後備，改成 `unreachable` 會變成未定義行為，反而比較不安全 |
| `std::ranges::contains`：`isOfferedTile` | **採用** | 選項放在一個 `constexpr std::array kOfferedTiles{0, 160, 256, 352, 448}`，另加 `static_assert` 檢查邊界。`SettingsDialog.cpp:25` 還有一份相同的清單，屬於 UI，本輪未合併 |
| `std::format` | **採用**（只限有數字轉換的地方） | `TileProcessor`、`ModelContract::resolveVerified` 的錯誤字串，內容不變。只是字串相接的地方不改 |
| C++26 | 未使用 | 沒有用 `submdspan` 等；`-std:c++23` 下也沒有 |

### 4.2 commit

| commit | 內容 |

### 4.3 注意事項

- **`tile_runner_anytile` 的字串替換**：probe 的 `CMakeLists.txt` 在 configure 時，會把 `TileProcessor.cpp` 裡的 `if (!ModelContract::isValidTile(p.tileRule, tile))` 換成較寬的檢查。這一行刻意保持原樣，並在它上方加了註解。
- **測試修改**：
  - `tst_inference_core` 原本檢查「出錯時 `out.pixels` 是空的」，現在改成檢查「沒有值且 `error().kind` 正確」。
  - 新增 `makeTilePlan` 的錯誤案例：tile 250、空圖。
  - 測試總數有增加，沒有刪減任何檢查項目。

|---|---|---|

### 6.2 CPU 端微基準（只跑 tiler，假引擎）

- **方法**：只把 `TileProcessor.cpp` 用和 release 相同的 cl 旗標（`/O2 /Ob2 /DNDEBUG -std:c++23 -MD`）編兩份：
  - 改動前：`5f25755`。
  - 改動後：工作目錄。
- **假引擎**：做最近鄰裁切，兩份相同。
- **量法**：每個案例取 7 次中的最小值。
- **結果**：三個案例輸出的 checksum，兩份都相同。原始碼在 scratchpad，未提交。

| 案例 | 改動前（ms） | 逐元素三維下標（ms） | 只算列起點，最終版（ms） |
|---|---|---|---|
| RGB 2400×1606 2× t256 | 481.5／484.8 | 509.8／508.9（+5%） | 486.8 → 486.1（6 輪取最小） |
| RGBA 1332×864 2× t160 | 312.3／315.4 | 331.3／336.4（+6%） | 315.9 → 320.1 |
| RGBA 666×432 4× t256 | 289.1／288.0 | 296.3／296.7（+3%） | 287.1 → 290.4 |

依規則，逐元素的寫法變慢，所以退回原本「列指標加內層迴圈」的寫法，只讓 mdspan 負責算位移；最終版和改動前相差在 1.3% 內，屬於雜訊。
