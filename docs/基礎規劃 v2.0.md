## 1. 狀態標示與範圍

### 1.1 保留的產品功能

**【既定】** 保留 Qt Widgets UI、目前版面與 Windows 淺／深色主題、清單縮圖、預覽、單張與批次處理、單張／批次進度條、剩餘時間估算、取消、完成摘要、資料夾與語言記憶。

保留繁體中文／日文／英文；英文為原始字串，另外兩語使用既有 `.ts`／內嵌 `.qm` 流程。保留 PNG／JPEG／WebP 輸入輸出、JPEG 品質及 WebP 有損／無損設定，不擴增動畫或 HDR 功能。

保留 1× 降噪、2×／4× 放大及既有降噪選項的使用者需求。模型對應必須實測，不能把舊 CUnet 的同一降噪數字宣稱為相同畫質或強度。1× 且不降噪仍視為無有效 AI 操作，除非日後另有明確決策。

### 1.2 排除項目

**【既定】** 正式執行環境不依賴 Python／PyTorch，不保留舊引擎 EXE、舊 NCNN 模型或 Vulkan 推論備援。

**【建議】** v2.0 首版不加入照片專用模型、訓練、TTA、影片、動畫、HDR、額外圖片格式、多 GPU 並行或自動模型市集。Python 可作為開發期模型匯出與參考結果工具，不隨正式包發行。

## 3. Windows ML API 與部署邊界

### 3.1 API 路線

**【既定】** 使用 Windows ML 所供應的 ONNX Runtime 正式 C API／C++ 封裝進行 Session、Tensor、Run 與錯誤處理。Windows ML 的 EP 探索、下載、註冊能力另由相應的正式管理 API 接入。

不要混淆以下三件事：

1. Windows ML 所供應的 ONNX Runtime C/C++ 推論介面：本案指定路線。
2. Windows ML 的 EP catalog／管理介面：依部署版本研究如何與 Qt 程式整合；可能需要少量 C++/WinRT、初始化與 apartment 管理，不代表重寫 UI。
3. 新的 Windows ML Runtime API：官方目前標為 experimental、不適合 production；本案不採用。也不以舊版 `Windows.AI.MachineLearning` 高階 WinRT 推論路線代替本案選擇。[Runtime API 狀態](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/runtime/overview)

**【待驗證】** 明列實際使用的套件匯入方式、CMake targets、API 簽章、WinRT 初始化位置、EP 註冊順序及關閉順序。本文模組名稱是設計名稱，不宣稱 SDK 存在同名類別。

### 3.2 自包含部署

**【建議】** 從 `Microsoft.Windows.AI.MachineLearning` 的 C/C++ self-contained 路線做獨立測試。官方部署文件列出 C/C++ 的自包含方式及 `build/cmake` 整合，並區分其與 framework-dependent 部署；不要直接照搬 C# 的安裝步驟。[官方部署文件](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/distributing-your-app)

**【待驗證】** 套件對應的最低 Windows build、Qt 的最低系統要求、VC Runtime、DirectX／驅動、RegFree WinRT／manifest 需求與離線啟動。最終最低 OS 取所有必要元件要求的交集，不直接沿用舊版 Windows 10 1809 宣告。

官方文件對 `Microsoft.Windows.AI.MachineLearning` 路線列出 Build 18362 起的情境，但這不能代替所選 C/C++ 套件及完整產品的部署實測。EP 動態下載門檻另外計算。套件大小及 DLL 清單以實際封裝結果為準，不預先承諾固定增加容量。

## 4. 建議架構與責任

```text
Qt Widgets：MainWindow／SettingsDialog／PreviewPane／語言與主題
    ↓ 不可變 JobSpec、取消請求；↑ queued 進度與結果事件
JobWorker → BatchRunner → ProcessJob（單項協調／安全提交）
                              ↓
                 ImagePipeline（讀圖／色彩／Alpha／編碼）
                              ↓
                 TileProcessor（計畫／padding／裁切／拼接）
                              ↓
                 WindowsMLEngine（ORT Session／Tensor／Run）
                       ↙                    ↘
             ModelManager              ExecutionProviderManager
          manifest／雜湊／契約         探索／註冊／選擇／診斷
                              ↓
           Windows ML 的 ORT + 已驗證 EP + nunif ONNX
```

**【建議】** 保留現有控制流程，不必另外建立與 `BatchRunner` 重複的 Controller。先抽出引擎／Tile 邊界，再視複雜度拆分 `ImagePipeline`。

| 模組（新名稱均為建議） | 責任與約束 |
|---|---|
| `InferenceOptions` | 模型 ID、倍率、降噪、Tile 策略、EP／裝置偏好；不再攜帶舊 EXE／模型目錄 |
| `ModelManager` | 驗證 manifest、檔案雜湊、I/O 契約與可用功能；拒絕不支援組合 |
| `ExecutionProviderManager` | 可用與已安裝 EP、裝置身分、版本／能力、選擇結果與失敗原因；不在 UI 執行緒下載或建立 Session |
| `WindowsMLEngine` | RAII 管理 Env／Session／RunOptions／Tensor；回傳分類錯誤，不依賴 stderr 文字判斷 |
| `TileProcessor` | 依模型契約產生 Tile、執行、檢查尺寸、裁切／融合、拼接、取消與有界重試 |
| `ImagePipeline` | 延續既有讀寫規則，明確管理 RGB／Alpha、stride、色彩、量化與緩衝區生命週期 |
| `ProcessJob` | 前置檢查、協調流程、錯誤轉換、暫存輸出與不覆寫提交 |
| `Progress` | 階段事件與 Tile 實際進度；整體時間仍為估算 |

每批預設單一 GPU 工作，不同圖片依序處理。相同模型／EP／裝置／精度／必要 shape 設定可重用 Session，但限制快取大小；切換組合時釋放不再使用的資源。Session、Tensor 與像素緩衝區不得在 Run 尚未結束時銷毀。

## 6. 模型取得、契約與相容性

### 6.1 候選系列與操作對應

**【建議】** 先研究 nunif `swin_unet/art`。當日官方 exporter 有 1× noise、2×／4× scale 與 noise-scale 的匯出路徑，但這只證明上游設計有這些輸出，不能證明指定 Release ZIP 內含全部檔案或能在 Windows ML 使用。[官方 exporter](https://github.com/nagadomi/nunif/blob/master/waifu2x/export_onnx.py)、[ONNX 資產取得說明](https://github.com/nagadomi/nunif/blob/master/waifu2x/unlimited_waifu2x/README.md)

| 操作 | 候選模型語義 | 驗證要求 |
|---|---|---|
| 1× 降噪 | noise0～3 類 | 尺寸與降噪效果、邊界 offset、輸入輸出契約 |
| 2× 放大 | scale2x 類 | 原生或衍生模型的實際行為、尺寸與畫質 |
| 2× 降噪放大 | noiseN_scale2x 類 | 每個預定提供等級均可載入並輸出正確 |
| 4× 放大 | scale4x 類 | 優先原生 4×；量測記憶體、畫質與拼接 |
| 4× 降噪放大 | noiseN_scale4x 類 | 各等級、尺寸與最終輸出限制 |

若原生 4× 不可行，Claude 應提出阻礙與證據。兩次 nunif ONNX 2× 只能作為待審替代方案，不能偷偷改變規格；即使採用也不恢復 NCNN 引擎。暫不直接採用開發中的 v3 系列；其發布狀態、授權與相容性須另查。

### 6.2 每個模型必填的 manifest／證據

- 模型 ID、相對路徑、來源 URL、Release／commit、資產名稱、下載日期、檔案大小、SHA-256。
- 系列／領域、倍率、降噪語義、精度、opset／IR、external data 依賴及其雜湊。
- 輸入／輸出名稱、個數、dtype、layout、固定或動態 shape、batch、RGB/BGR、值域與正規化。
- 模型輸入尺寸與有效輸出尺寸關係、offset 的座標單位、合法 Tile 最小值／步長／對齊、padding、halo／overlap 與融合規則。
- Alpha 與前後處理契約、是否依賴額外 helper model；必要 helper 同樣驗證與授權。
- 相容性結果：套件／ORT／EP／GPU／驅動／OS／Tile／精度，以及通過日期。
- 模型／權重／匯出程式各自授權、證據檔與再散布判定。

**【待驗證】** 不假定輸出就是輸入乘倍率；有效區域可能需要裁切。以固定版本的上游參考實作對照，還原完整前後處理。小尺寸、奇數尺寸、窄圖、非對齊尺寸及透明邊界都要有一般案例。

先用 FP32 建立參考。FP16、圖最佳化、固定 shape 或重新匯出，都必須記錄轉換工具版本並重做相容性與畫質比較。ONNX checker 通過、CPU 可執行、Web 版可執行、Session 建立成功，各自都不能代替目標 GPU 的端到端驗證。

## 7. EP、DirectML 與硬體選擇

**【基準已核對】** Windows ML 目前列有內含 CPU、DirectML（legacy）；廠商 EP 另行取得。EP catalog 動態下載需要 Windows 11 24H2／build 26100 以上及相符硬體、驅動。這與自包含 Runtime 的最低 OS 是不同條件。[官方 EP 清單與要求](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers)

### 7.1 建議選擇流程

1. 啟動時只檢查本機 Runtime 與已安裝 EP；預設不自動下載全部廠商 EP。
2. 依所選模型、已驗證能力、裝置與驅動選擇 EP。不要只按廠牌或「GPU 存在」判定可用。
3. **Auto 模式建議**：已安裝且該模型已驗證的硬體最佳化 EP → 已驗證的 DirectML 路徑。優先級可依實測調整，不能認定廠商 EP 永遠較快。
4. 初始化／首個測試失敗可作有限次下一候選嘗試；記錄原因。使用者明確指定某 EP 時，失敗應報錯，不偷偷換裝置。
5. 整張轉 CPU 應由使用者明確選擇；不要在 GPU 失敗後自動跑數十分鐘。
6. Runtime 內部仍可能把部分節點分配給 CPU。這與「整張 CPU 模式」不同；必須在 probe 檢查節點分配／profiling，避免顯示 GPU 名稱就宣稱全程 GPU。
7. 廠商 EP 下載為獨立操作，顯示用途、下載狀態與失敗結果；離線仍可使用已驗證的內含路徑。首次下載不可混在圖片處理進度裡。

GTX 1060 應列為 DirectML **待測** 裝置；官方 NvTensorRtRtx 要求 RTX 30XX 以上，不能將 GTX 1060 排入該路徑。NVIDIA／AMD／Intel 的實際支援範圍只列已測組合；不因宣稱支援 DirectX 12 就保證 nunif 全模型可用。NPU 不列首版必要驗收。

多 GPU／內顯與獨顯：保存穩定裝置身分、EP 與驅動資訊，不能只存每次啟動可能變動的索引。UI 顯示實際選用裝置；選用 API 的能力與穩定識別方式待套件驗證。

### 7.2 DirectML 專項

官方 ORT DirectML 文件指出 memory pattern／parallel execution 限制，以及同 Session 不支援多執行緒同時 Run。應依所選套件標頭設定對應選項，並以單 Session、順序 Tile 起步。[DirectML 文件](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)

**【待驗證】** 運算子／opset／dtype 支援、動態 shape、padding 算子、張量尺寸上限、GPU 記憶體配置及裝置遺失行為。廠商 EP 的限制分別查證，不能把 DirectML 的設定或成功結果套用給其他 EP。

## 8. Tile、記憶體與尺寸上限

### 8.1 尺寸政策

**【既定，初期沿用】** 使用十進位 MP：1 MP = 1,000,000 像素。輸入最多 4,500,000 像素；最終輸出最多 75,000,000 像素。

`outputPixels = inputWidth × inputHeight × scale²`，使用溢位安全計算。4× 是每邊乘四、面積乘十六，所以滿 4.5 MP 輸入最多輸出 **72 MP**；75 MP 是獨立防線，不是要靠 padding 擴張至 75 MP。

同時維持格式單邊限制：目前程式 WebP 為 16,383、JPEG 為 65,500，PNG 無另設格式單邊上限；仍受實際編碼器、整數與配置限制。實作依既有已驗證套件核對，不因 MP 合格就略過單邊檢查。模型 padding 尺寸與最終影像尺寸分開檢查，輸出必須裁回精確目標尺寸。

### 8.2 Tile 規則

**【建議】** Auto Tile 使用實測的保守值與有限候選序列；不要直接沿用 NCNN 的 100／200／400。依模型對齊規則計算實際輸入 Tile，區分「有效核心區域」與「含 halo／padding 的張量尺寸」。

- 依上游規則處理 reflection／replication padding、offset、有效區域裁切與 overlap／seam blending；禁止只切四方格再硬拼。
- 核心區覆蓋整張圖，邊角無漏像素；重疊區如何累加、權重正規化、何時量化都要寫明。
- 分塊與上游參考結果比較，檢查細線、平塗、漸層、文字、透明邊緣；不能靠加模糊掩蓋接縫。
- 單張預設逐 Tile 推論；先不建立多 Tile 同時 Run 或無界張量預取。
- 預設 Auto 遇到明確可恢復的記憶體不足，最多縮小 Tile 重試一次。釋放緩衝區／必要時重建 Session，再從該圖片乾淨狀態開始；失敗即結束該項。
- 裝置遺失、模型錯誤與未知異常不當作 OOM 無限重試。手動 Tile 的重試政策需明示，不偷偷改畫質或倍率。

### 8.3 CPU／GPU 記憶體分開估算

Tile 限制的是單次推論張量與中間活化，不能保證整張結果放得進 RAM。

75 MP 的 RGB8 約 225 MB、RGBA8 約 300 MB、RGB FP32 約 900 MB，以上是十進位容量，尚未含其他副本與編碼器記憶體。因此不要同時保留整張 FP32 輸出、整張浮點融合權重、RGBA 結果與多份編碼副本。

**【建議】** 優先重用小型 Tile 緩衝區，使用單一必要的全圖 8-bit 結果；融合若需要浮點累加，研究條帶／有限窗口，證明數學與上游一致。先評估簡單全圖方案的實際峰值，再決定是否需要複雜的串流，不預設 Qt 編碼器支援任意逐列串流。

配置前檢查乘法溢位、實際合法 shape 與預估容量；配置失敗回報可理解錯誤。VRAM 預估只作提示，不能視為已保留容量。記錄峰值 RAM／可取得的 GPU 記憶體、Tile、速度；不以為移除中繼 PNG 就必然更省記憶體。

## 9. 像素、色彩與 Alpha

**【基準已核對】** 目前只接受 8-bit PNG／JPEG／WebP，拒絕動畫／多影格與高位深／HDR；使用 EXIF 自動轉向，將有效非 sRGB profile 轉為 sRGB，輸出為不帶標籤的 sRGB。JPEG 透明區合成白底。這些行為應保留或明確列為相容性決策。

**【待驗證】** nunif 模型是否只處理 RGB，Alpha 如何放大、透明區 RGB 是否先做邊界延伸、premultiplied／straight alpha 的轉換與拼接順序。應對照固定版本上游參考，避免黑邊、白邊與透明色滲漏；不將 Alpha 直接塞入三通道模型。

QImage 的 scanline stride、RGB/BGR、資料連續性、張量 NCHW／NHWC、正規化值域、clamp／round、NaN／Inf 與輸出數量均明確驗證。預覽與正式輸出使用同一結果／色彩契約，避免看起來不同。

## 10. 取消、進度與錯誤

### 10.1 取消與關閉

**【建議】** 狀態流程為：待命 → 前檢／載入模型 → 解碼 → Tile 推論／拼接 → 編碼 → 提交 → 完成。各狀態可進入取消或錯誤；提交是明確的完成邊界。

- 沿用 atomic cancel；Tile 前後、拼接、編碼前後及提交前檢查。已完成檔案保留，當前未提交檔案清理，後續批次項目不執行。
- 最小承諾是目前 Tile 返回後停止，不保證任意 GPU kernel 立即中斷。ORT RunOptions 的終止能力與對應 C/C++ API、各 EP 是否有效，要在選定版本查證並實測後才啟用。
- 禁止 `QThread::terminate`、釋放執行中的 Session 或強行銷毀 Tensor。UI 顯示「正在取消」並保持事件迴圈可回應。
- 編碼器若無中途取消能力，等待本次編碼返回再刪暫存檔；清楚記錄此延遲。
- 按取消與最終提交同時發生時，定義線性化邊界：提交已成功則該項是成功，不能把已存在的完整輸出誤報為未輸出，也不事後刪掉成功檔案。
- 視窗關閉時請求取消並等 worker 安全結束。若 GPU／驅動可能長時間不返回，需評估體驗與是否另設推論 worker process；此為待研究架構選項，不是本案已承諾的即時終止功能。

### 10.2 進度與 ETA

保留既有進度條，讓 `stageFraction` 接收真正完成並拼接的 Tile 工作量。等大小 Tile 可用完成數／總數；邊緣大小不一或多階段時依有效像素或估計工作量加權。它反映已完成工作，並非正在執行 kernel 的精確百分比。

模型下載、Session 編譯／暖機、解碼、編碼／提交要單獨表示；沒有可靠進度時用階段提示或估算。最終檔案提交成功才到 100%。OOM 重啟該圖時提示「重新嘗試」，以 attempt 或重新規劃解釋進度，不假造單調的真實完成率。

ETA 以模型雜湊、EP、裝置／驅動、精度、倍率、Tile 等必要維度分組；冷啟動與暖機分開。重設舊 NCNN 學習速率；尚無資料顯示估算中。不要把 Tile 完成率宣稱為整體時間的準確比例。

### 10.3 錯誤分類

| 類型 | 建議處理 |
|---|---|
| 壞圖、超限、單張編碼失敗 | 記錄該項失敗，依既有政策繼續批次 |
| 模型缺失／雜湊錯誤／I/O 契約不符 | 批次前攔截或 fatal；不以別的模型靜默替代 |
| Runtime 缺失、EP 初始化失敗 | 前檢回報；Auto 僅允許有界且可診斷的候選切換 |
| 可恢復 OOM | 限定一次縮 Tile；仍失敗則停止該項，確認引擎健康後才繼續 |
| 裝置遺失／Session 不可信 | 停止批次，釋放資源；不在損壞狀態繼續跑 |
| 使用者取消 | 獨立結果，不計為一般失敗 |

診斷至少包含模型 ID／雜湊、Runtime／EP 版本、裝置、Tile／shape、階段、原始錯誤碼；三語 UI 顯示易讀摘要。不要依賴上游英文錯誤字串做唯一控制流程，也不要記錄圖片內容或不必要的完整私人路徑。

## 11. 安全、授權與發布

1. 延續不覆寫原圖／現有輸出的規則。輸出目錄建立本工作專屬暫存檔，完成編碼、flush／close／尺寸驗證後才用既有安全命名流程提交；失敗只刪本工作建立的檔案。
2. 不要用會覆寫既有檔案的原子替換 API，取代目前不覆寫的提交語義。名稱碰撞、寫入失敗、取消及輸入輸出同資料夾須做必要安全回歸。
3. Runtime／模型取得使用鎖定來源與預期雜湊；解壓檢查路徑越界。載入可信 app 目錄的 DLL／模型，不從目前工作目錄或任意設定路徑搜尋未知 DLL。不把雜湊驗證宣稱為發行者簽章驗證。
4. Windows ML／ORT／DirectML／廠商 EP／模型／helper／Qt／VC Runtime 各自核對散布條款。廠商 EP 可下載不等於可以直接再打包。
5. 保留 Qt LGPL／第三方通知、對應來源與可替換動態庫等既有交付安排；按最終元件逐項確認，不能因移除推論 Vulkan 就移除 Qt 仍需要的 Vulkan 相關通知。
6. 封裝使用新的乾淨 staging、明確 allowlist 與依賴檢查，防止從舊 build／dist 帶入 EXE、NCNN 模型或無關 DLL。安全清理只限已確認工作目錄，不動歷史 Release。
7. 發行包至少含程式／Qt plugins／必要 Runtime DLL／獲准模型與 manifest／授權通知／使用說明；另交付必要對應來源與 SHA256SUMS。實際 DLL 與檔案清單由部署驗證產出。
8. 離線第一次啟動、未安裝開發環境的 Windows 上，驗證已宣告的推論路徑與錯誤提示。缺少廠商 EP 時不應默默連網或讓 UI 卡住。
9. 最低 OS、已測 GPU／驅動、未測平台、簽章狀態、CPU 模式及取消限制如實記錄。不得把開發機成功描述為所有 Windows／所有 GPU 已驗證。

- [ ] 至少在實際目標 GPU 的 Windows ML／DirectML 路徑驗證；若使用者目標是 GTX 1060，需該卡實測才能宣稱支援該卡。
- [ ] 廠商 EP 若納入首版選項，對應組合需有文件與可取得硬體上的實測；未測選項不默認啟用，也不聲稱全品牌支援。
- [ ] 小圖與非對齊尺寸正確；4× 輸出每邊精確乘四；Tile 無可見接縫、缺塊或邊角偏移。
- [ ] 與固定上游參考圖比較，事先訂定數值誤差方法／容許值並人工檢查代表圖；不要求不同 EP 逐位元相同，不預先捏造 PSNR 門檻。
- [ ] PNG／JPEG／WebP、透明圖、JPEG 白底、WebP 有損／無損與色彩契約符合保留規格。
- [ ] 輸入 4.5 MP、輸出 75 MP、格式單邊限制及溢位安全檢查有效；代表性滿尺寸案例可完成或回報清楚且安全的資源不足錯誤。若宣稱完整上限可用，須有該上限成功證據。

### 14.2 操作、安全與回歸

- [ ] 批次有成功／失敗／未處理摘要；單張壞圖可按政策繼續，共享引擎錯誤停止。
- [ ] 推論期間與編碼／提交附近取消均符合明訂邊界；不產生看似成功的半成品，不刪除既有檔案。
- [ ] 原圖不變、重名不覆寫、輸入輸出同目錄安全；可控制的寫入失敗可回復。
- [ ] UI 可回應；單張／批次進度有 Tile 完成資料；ETA 清楚是估計，提交前不顯示完成。
- [ ] 繁中／日文／英文、預覽／縮圖、淺深色、資料夾記憶及設定遷移通過必要回歸。
- [ ] Auto 不偷偷切整張 CPU、不首次啟動就下載廠商 EP；缺模型／Runtime／EP 的提示可理解。

### 14.3 發布

- [ ] Release 與執行路徑完全不包含或呼叫 waifu2x-ncnn-vulkan、models-cunet／NCNN 舊推論模型。
- [ ] 模型與 Runtime 版本固定、雜湊可核對；授權／通知／對應來源完整。
- [ ] 乾淨 staging 的 Portable ZIP 在宣告的非開發環境可啟動並處理代表圖片；離線路徑通過。
- [ ] 版本、最低 OS、已測硬體、簽章狀態與未測限制如實寫入說明。

以上清單全部依證據完成，才可將「已決定的新引擎方向」提升為「已驗證可發布的 v2.0」。若只完成 probe，結論應止於該模型、該 EP、該環境的可行性。
