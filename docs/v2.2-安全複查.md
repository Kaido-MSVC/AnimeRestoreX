**已確認沒問題：原來依賴 `qUncompress()` 提示值的無上限解壓已移除，正式呼叫點同時限制壓縮資料與解壓結果。**

兩個需要精確表述的限制，不列為新的安全發現：

- **正常回傳有清理，不等於 C++ 例外也有清理。** `ImageMetadata.cpp:583–586,595` 的錯誤字串或 QByteArray 配置若丟出例外，手動 `inflateEnd()` 會被跳過；目前不是 RAII。這需要額外的配置失敗條件，不能把受限圖片直接說成必然可觸發洩漏或當機；本次未證明可恢復例外後反覆累積。日後整理 OOM 處理時可改 scope guard，不因這項一般低記憶體條件阻擋此次 S-01 修正。
- **32 MiB 限的是輸出資料長度，不是程序 RSS 的精確上限。** QByteArray 容量成長、壓縮輸入、暫存與 Qt 解碼仍有成本；超限檢查最多額外解出一個 64 KiB 步驟，但不會把它追加到 out。故 header 註解 `ImageMetadata.h:45–48` 的配置描述不宜被解讀為整個程序最多只多用 32 MiB＋64 KiB。

**ICC 使用前的檢查：** `inflateLimited()` 證明的是 zlib 串流完整及大小受限，不是完整 ICC 格式驗證；`iccColorSpace()`（`ImageMetadata.cpp:601–604`）只要求至少 128 bytes 並讀取 RGB／GRAY 欄位，`ImageLoader.cpp:142–145` 再依來源與色彩空間決定保留。沒有驗證 ICC 宣告長度、`acsp` 或全部 tag 範圍，結尾多餘壓縮 bytes 也未強制拒絕。這是原本「保留描述檔原始 bytes」的既有策略，本次沒有新增自行解參照 ICC tag 的操作，未找到由此繞過解壓上限或造成新的越界；完整 ICC sanitizer 不列為發布必要條件。若未來要求只輸出有效 ICC，可另加格式驗證，但不能把本次解壓成功稱為 ICC 已完整驗證。

**預覽／縮圖的範圍：** ExifOnly 保證的是本專案的 metadata reader 不讀取／解壓 ICC；Qt 在標頭辨識與像素解碼時仍可能處理來源 ICC。這次沒有替換 Qt 的 libpng／zlib，也沒有宣稱連 Qt 都不接觸 ICC。既有整體載入測試涵蓋此差異，沒有找到新增的自寫旁路。

### S-02：通過

**已確認沒問題：原先短檔宣告約 2 GiB IHDR 就先配置的攻擊情境已被擋下。**

- `ImageMetadata.cpp:64–79` 要求第一個 chunk 是 IHDR、長度恰為 13；用 `std::array<char,13>` 讀取。錯誤長度、不在第一個或重複的 IHDR 不會進入動態長度配置，並清空目前 metadata。超過 PNG 允許的 31-bit chunk 長度也在 `:60–61` 直接返回。
- **可 seek：** `fitsRemaining()`（`:46–48`）採 `len <= size - pos`，PNG 在 `:95–97`、WebP 在 `:216–218` 先檢查後 resize；檔案僅有宣告長度、實際資料不足時，不會先配置該宣告量。呼叫前的 len 非負且已受 32 MiB／4 MiB 上限限制，沒有從加法溢位繞過的路徑。
- **不可 seek／sequential：** `fitsRemaining()` 明確回傳 true，故**仍可能先配置最多 32 MiB ICC 或 4 MiB EXIF，再發現短讀**；不是所有 QIODevice 都做了剩餘長度驗證。但上限在 resize 之前仍生效，IHDR 仍固定 13 bytes，JPEG segment 最多 65533 bytes；沒有恢復原來約 2 GiB 的無界配置。正式圖片入口 `read(path)`（`:557–562`）使用 QFile，未找到 GUI 把網路串流等 sequential 裝置送進來的路徑，因此此有限配置不列漏洞。
- `fitsRemaining()` 檢查的是 payload；PNG CRC 與 WebP 奇數填補是在讀取後另查（`:104,229`）。僅缺 CRC／填補可能在配置後才失敗，但最多仍是上述有限配置，不是 S-02 繞過。sequential 裝置若暫時只交付部分資料，`readExact()` 會直接視為失敗，這是目前同步解析的限制，沒有新網路功能依賴它。

原修正紀錄的「非法 IHDR 一律清空」也不宜擴張為完整 PNG 有效性保證：例如讀到已有 metadata 後，若某 chunk 長度大於 0x7fffffff，`:60–61` 是直接返回，並非先清空。這不會配置大區塊，也不影響本次資源安全修正，無須為此新增發布阻擋項。

### S-03：需要修改

**已確認沒問題的部分：** `ImageMetadata.cpp:722–747` 現在會拒絕 IFD1 解析失敗、next IFD、offset／length 缺一、count 非 1、型別非 SHORT／LONG、零長度、資料超出區塊以及和保留區重疊。offset 為 0 即使先通過 `has()`，也會因重疊 TIFF header 而拒絕。

正常單一 JPEG／strip 縮圖的範圍會加入 dropped，IFD1 表與已知 out-of-line values 亦由 `parseIfd()` 加入，`:748–754` 清零，位於最後時再截斷。`ProcessJob.cpp:515–525` 在 prepareExif 失敗時不填 extras.exif，故輸出不寫 EXIF 的整合路徑正確。現有測試確認 raw bytes 的方向也正確，不只檢查 IFD1 指標（`tests/tst_core.cpp:951–962`）；pipeline 亦有不寫 EXIF 的案例（`tests/tst_pipeline.cpp:426–444`）。

| 編號 | 嚴重度／狀態 | 檔案:行號 | 問題與情境 | 修正建議 |
|---|---|---|---|---|
| R-01（S-03 未完整關閉） | **低／已確認**；未動態重現 | `src/core/ImageMetadata.cpp:311–325,330–334,727–754`；`src/core/ProcessJob.cpp:520–525` | IFD1 可以包含重複的 JPEGInterchangeFormat／Length 或 StripOffsets／ByteCounts。`parseIfd()` 不拒絕重複 tag，`findTag()` 只取第一個，因此只清除第一組指向的影像。如果區塊後面還有其他保留資料，truncate 不會執行，另一組指向的縮圖 bytes 會原樣保留，prepareExif 卻回傳成功並寫入輸出。使用者開啟「保留 EXIF」並分享結果時，接收者仍可能從原始 EXIF bytes 取得原圖縮圖；不表示一般看圖軟體仍會循 IFD1 顯示它，也不涉及程式碼執行。 | 最小修改是在清除前拒絕 IFD1 中重複的 `0x0201／0x0202／0x0111／0x0117`；更簡單可拒絕 IFD1 所有重複 tag。直接回傳既有 thumbnail cannot be removed 錯誤，讓上層略過整段 EXIF，不必嘗試猜哪個重複項目有效。 |

以下是可由程式碼逐步核對的靜態版面，不是本次執行的測試或已產生的圖片。所有區間皆為 TIFF 起點算起、右端不含：

| 區塊 | 配置 |
|---|---|
| TIFF header | `[0,8)`，IFD0 offset = 8 |
| IFD0 | `[8,26)`，一個 Make ASCII tag，count = 8，資料 offset = 2400；next 欄位在 22，指向 IFD1 = 40 |
| IFD1 | `[40,94)`，四個 LONG／count=1 entry：`0201=256`、`0201=1280`、`0202=1024`、`0202=1024`；next 欄位在 90，值為 0 |
| 縮圖資料 | 第一份 `[256,1280)`、第二份 `[1280,2304)`，各 1024 bytes，可容納實際 JPEG 縮圖資料 |
| 保留的 Make 值 | `[2400,2408)`，使 keptEnd = 2408 |

程式會把 IFD1 表 `[40,94)` 與**第一份** `[256,1280)` 加入 dropped；它們不與 kept 重疊，所以不拒絕。因 dropped 起點小於 keptEnd，`:753` 的條件為 false，不截斷；第二份 `[1280,2304)` 未清零，隨整個 QByteArray 回傳。兩種 TIFF 位元組順序都走相同判斷。

這是對損壞／歧義縮圖結構的清除缺口，與原 S-03 的隱私目標相同，並非要求清除所有任意未引用資料或 MakerNote。現有 `tests/tst_core.cpp:939–1004` 沒有重複 tag＋後方保留資料這個案例；補修後只需增加這個有限回歸，不必重跑推論品質或進行壓力測試。
