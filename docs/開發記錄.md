## 3. 上游 CLI 實測行為（20250915，本機）

`-h` 實際輸出的參數：`-n -1/0/1/2/3`、`-s 1/2/4/8/16/32`、`-t >=32/0=auto`、`-m`、`-g`（`-1` 表示 CPU，預設 auto）、`-j`、`-x`、`-f jpg/png/webp`。

| 情境 | exit code | stderr | 程式處理方式 |
|---|---|---|---|
| 正常 2×、4× | 0 | 只有 GPU 資訊行 `[0 NVIDIA ...]` | 驗證輸出檔尺寸是否剛好為 W·s × H·s |
| 模型路徑不含 `models-cunet` | -1 | `unknown model dir type` | 上游以路徑名稱判斷模型類型，所以安裝資料夾名稱必須固定為 `models-cunet` |
| 輸入檔解碼失敗 | **0** | `decode image ... failed` | exit code 不可靠；以「輸出檔存在且尺寸正確」判定成功 |
| GPU 編號不存在 | -1 | `invalid gpu device` | 轉為「找不到可用的 Vulkan GPU」訊息 |
| 中文、日文、空白路徑 | 0 | — | 可正常處理（主控台輸出的路徑會亂碼，不影響處理） |

## 5. A9 實機量測步驟（GTX 1060 6GB，由使用者執行）

準備：一張小圖（約 0.3 MP）和一張接近 4.5 MP 的動漫插畫（例如 3000×1500 或 2100×2100）。先執行 `build.ps1 -Preset release`。

1. 開啟工作管理員的「效能 → GPU」頁籤，觀察「專用 GPU 記憶體」；「詳細資料」頁籤加入「認可大小」欄。
2. 純推論耗時：在 PowerShell 執行下列指令。把 `<in>` 換成圖片路徑，`s` 分別用 2 和 4，`t` 分別用 0（自動）、200、100：
   ```powershell
   $w="D:\projects\AnimeRestoreX\build\release\waifu2x"
   Measure-Command { & "$w\waifu2x-ncnn-vulkan.exe" -i <in> -o "$env:TEMP\a9.png" -n 1 -s 4 -t 0 -m "$w\models-cunet" }
   ```

## 6. A9 結果與定案（2026-11-01）

### 使用者實測（GTX 1060 6GB，NVIDIA 581.80，waifu2x 直接執行）

輸入：1600×2171（3.47 MP）與 1200×675（0.81 MP）的動漫插畫，共 21 個案例全部成功。下表為 1600×2171 的數據：

- **直接 `-s 4` 與真正的兩階段**（臉部、頭髮兩區，4× 原生像素並排）：肉眼幾乎無差別。整張圖亮度差平均 0.42、最大 28；水平梯度平均（細節的粗略指標）`-s 4` 為 2.868，兩階段為 2.883。兩階段沒有變差，平滑程度略少。

## 16. 封裝文字檔的換行（2026-11-06，v2.0.0 發布後）

v2.0.0 打包時發現，`README.txt` 與 `models/manifest.json` 的位元組和 rc3 不同，內容其實一樣：`package.ps1` 直接複製工作目錄的檔案，`core.autocrlf=true` 下換行取決於檔案何時被 checkout。已發布的 v2.0.0 不重新封裝，只修正之後的建置。

## 18. v2.1 P0／P1：C++23（2026-11-13）

不加新功能，輸出與 v2.0.1 逐位元相同。詳細內容見 `docs/v2.1-P0-P1報告.md`。

- **P0**：
  - `CMAKE_CXX_STANDARD` 改成 23。CMake 4.4.4 會把 MSVC 的 C++23 對應到 `-std:c++latest`，所以 MSVC ≥ 19.52 時用 `CMAKE_CXX23_STANDARD_COMPILE_OPTION` 改成 `-std:c++23`；CMake 原生支援後就移除這段。
  - 原始碼不需要修改，`/W4` 沒有新警告。
  - `build.ps1`（主程式與 probe）的 `-vcvars_ver` 由 14.51 改成 14.52，因為 14.51 已經不在開發機上。
  - probe 也一起升到 C++23。
- **P1**：推論核心改用以下寫法：
  - `std::expected`：`makeTilePlan`、`upscaleImage`、`sha256File`、`resolveVerified`。
  - `std::mdspan`：平面緩衝區。熱點迴圈只用它算列起點，逐元素下標慢約 5%。
  - `views::cartesian_product`：tile 迴圈。
  - `ranges::contains`／`find`。
  - `std::format`：錯誤字串。
  - 跳過 `byteswap`、`flat_map`、`to_underlying`、`unreachable`、`enumerate`／`zip`，理由見報告 §4。
- **驗證**：
  - ctest 每個 commit 都是 5／5。
  - arx_verify 16 張 PNG（1×／2×／4×、透明、tile 256 與 160、CPU）對 v2.0.1 最大差 0。
  - 2400×1606 2× t256 的時間和基準（19.6–19.9 s）相同。

## 19. v2.1 P2：TTA（2026-11-13）

設定加入 TTA（預設關閉）。照 nunif 0d3d92c 的 `tta_split`／`tta_merge` 實作，詳細內容見 `docs/v2.1-P2報告.md`。

- **做法**：
  - 整張 RGB 做 8 種翻轉、旋轉，每種各跑一次完整的 tiled render。
  - 反變換後依上游順序加總，乘 1/8、clamp，再 quantize256。
  - alpha 不做 TTA，alpha border padding 在變換前做一次。
  - 1×、2×、4× 都能用。
- **記憶體**：
  - 各份直接累加進一個 float 緩衝區，不建變換後的複本，也不保留 8 份結果。
  - 每個輸出像素多 12 bytes；75 M 像素時，float 緩衝區由 1.2 GB 增加到 2.1 GB。
- **復原、取消與進度**：
  - GPU 復原時 8 份全部用 160 重做。
  - 取消照舊在每個 tile 之間檢查。
  - ETA 用獨立的速度分組（`/tta`）。
  - 完成清單標示「（TTA）」，diagnostics 記錄 `tta`。
- **驗證**：
  - TTA 關閉時 16 個案例對 v2.0.1 最大差 0。
  - TTA 開啟時對 nunif CLI `--tta` 的 4 個案例最大差 1。
  - 2400×1606 2× t256：TTA 關閉 19.6 s（與 P1 相同），開啟 113.4 s；峰值 private 多 176 MiB。
