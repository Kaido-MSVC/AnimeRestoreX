## 3. 上游 CLI 實測行為（20250915，本機）

`-h` 實際輸出的參數：`-n -1/0/1/2/3`、`-s 1/2/4/8/16/32`、`-t >=32/0=auto`、`-m`、`-g`（`-1` 表示 CPU，預設 auto）、`-j`、`-x`、`-f jpg/png/webp`。

| 情境 | exit code | stderr | 程式處理方式 |
|---|---|---|---|
| 正常 2×、4× | 0 | 只有 GPU 資訊行 `[0 NVIDIA ...]` | 驗證輸出檔尺寸是否剛好為 W·s × H·s |
| 模型路徑不含 `models-cunet` | -1 | `unknown model dir type` | 上游以路徑名稱判斷模型類型，所以安裝資料夾名稱必須固定為 `models-cunet` |
| 輸入檔解碼失敗 | **0** | `decode image ... failed` | exit code 不可靠；以「輸出檔存在且尺寸正確」判定成功 |
| GPU 編號不存在 | -1 | `invalid gpu device` | 轉為「找不到可用的 Vulkan GPU」訊息 |
| 中文、日文、空白路徑 | 0 | — | 可正常處理（主控台輸出的路徑會亂碼，不影響處理） |

## 5. A9 實機量測步驟（GTX 1060 6GB，由使用者執行）

準備：一張小圖（約 0.3 MP）和一張接近 4.5 MP 的動漫插畫（例如 3000×1500 或 2100×2100）。先執行 `build.ps1 -Preset release`。

1. 開啟工作管理員的「效能 → GPU」頁籤，觀察「專用 GPU 記憶體」；「詳細資料」頁籤加入「認可大小」欄。
2. 純推論耗時：在 PowerShell 執行下列指令。把 `<in>` 換成圖片路徑，`s` 分別用 2 和 4，`t` 分別用 0（自動）、200、100：
   ```powershell
   $w="D:\projects\AnimeRestoreX\build\release\waifu2x"
   Measure-Command { & "$w\waifu2x-ncnn-vulkan.exe" -i <in> -o "$env:TEMP\a9.png" -n 1 -s 4 -t 0 -m "$w\models-cunet" }
   ```

## 6. A9 結果與定案（2026-11-01）

### 使用者實測（GTX 1060 6GB，NVIDIA 581.80，waifu2x 直接執行）

輸入：1600×2171（3.47 MP）與 1200×675（0.81 MP）的動漫插畫，共 21 個案例全部成功。下表為 1600×2171 的數據：

| 案例 | tile | 引擎耗時 | waifu2x RAM 峰值 | GPU 增量（整卡峰值 − 基準） |
|---|---|---|---|---|
| 2×，降噪 1 | 自動 | 6.1 s | 239 MiB | 989 MiB |
| 2×，降噪 1 | 200 | 6.2 s | 236 MiB | 285 MiB |
| 4×（`-s 4`），降噪 1 | 自動 | 13.7 s | 469 MiB | 989 MiB |
| 4×（`-s 4`），降噪 1 | 200 | 14.5 s | 455 MiB | 285 MiB |
| 2×，降噪 0／1／2／3 | 自動 | 3.6–3.9 s | 約 208 MiB | 990 MiB |

1200×675 的 4×（`-s 4`）約 3.7–3.9 s，RAM 約 200–211 MiB。

**量測中的錯誤**：A9 的「兩階段」案例，最終輸出與 `-s 4` 的輸出**逐位元組相同**（tile 自動與 200 都是如此）。原因是量測腳本設計上兩次都用 `-n N`（用來對照上游 `-s 4`），並非 `-n -1`，所以該組數據並未測到定案的方案，不採用。Claude 另以 A9 第一階段的 2× 輸出重跑 `-n -1 -s 2`，耗時 11.9 s，因此**真正兩階段的總耗時約 18 s**（6.1 + 11.9，只測一次），比 `-s 4` 慢約 30%。

### 輸出圖比較（Claude，依 A9 輸出檔）

- **直接 `-s 4` 與真正的兩階段**（臉部、頭髮兩區，4× 原生像素並排）：肉眼幾乎無差別。整張圖亮度差平均 0.42、最大 28；水平梯度平均（細節的粗略指標）`-s 4` 為 2.868，兩階段為 2.883。兩階段沒有變差，平滑程度略少。
- **降噪 0–3**（2×）：此原圖較乾淨，差異細微；3 級的漸層與膚色稍平滑，1 級沒有可見的細節損失。
- **tile 接縫**：放大 tile 200 的邊界交叉點，看不出接縫；tile 200 與 tile 自動的差異放大 8 倍後幾乎全黑，也沒有沿邊界集中（邊界欄的差異平均 0.278，其他欄 0.298）。整張圖逐欄／逐列的梯度，在 tile 邊界處的比值為 0.94–1.07，非邊界處為 0.97–1.19，沒有接縫跡象。tile 200 下的真正兩階段沒有另外產生輸出，但 tile 的切分方式與第二次 2× 相同。

### 定案

| 項目 | 決定 | 實作 |
|---|---|---|
| 降噪預設 | **1** | `AppSettings::kDefaultNoise = 1` |
| tile 預設 | **自動** | `AppSettings::kDefaultTile = 0`；設定視窗保留 400／200／100，處理大圖失敗時可改小（tile 200 的 GPU 增量約 285 MiB） |
| 4× 實作 | **兩階段**：`-n N -s 2` → `-n -1 -s 2`，降噪只執行一次 | `Waifu2xRunner::passes()`；ProcessJob 逐階段驗證輸出尺寸，中間的 2× 暫存檔用完即刪；4× 另需 `scale2.0x_model`（開始前檢查）。測試 `fourXIsTwoStage` 證實輸出與手動兩階段逐像素相同，且不同於 `-s 4` |
| 尺寸上限 | **維持 4.5 MP 輸入／75 MP 輸出** | 實測最大 3.47 MP（約 3.5 MP）；4.5 MP 為依比例推估：RAM 與耗時大致隨像素數線性成長，4.5 MP 的 4× 預估約 600 MiB、兩階段約 23 s，**尚未實測** |
| 開發用比較方式 | 移除 `tools/measure-a9.ps1` | A9 量測腳本，只供開發使用，從未放進發行包；產品程式中沒有對應的開關。腳本的「兩階段」依其設計兩次都用相同的 `-n N`（腳本第 10、245 行），所以結果與 `-s 4` 完全相同。腳本內容保留在 git 歷史 commit `b8d4664` |
