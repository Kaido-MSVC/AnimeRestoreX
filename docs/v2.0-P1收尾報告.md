## 2. 非法 tile

### 2.1 上次為什麼一致

- **沒有切塊**：P1 的 `illegal` stage 把一張 T×T 的輸入直接餵給模型，只跑一次前向，沒有 tile 融合，也沒有邊緣 tile。
- **結構上可行**：v3 只有一處尺寸限制，`WindowMHA2dV2.forward` 的 `assert H % window == 0`。特徵圖是 T/2、window 是 8，所以需要 `T % 16 == 0`，400 和 240 都符合；ONNX 圖裡沒有這個 assert。上游的 `T % 32 == 0` 比結構需求嚴格，原始碼沒有說明原因。

另外兩點：

- nunif CLI 不能當 400 的參考：`find_valid_tile_size` 會把 400 無聲降到 384、240 降到 224。
- 主程式的 `makeTilePlan` 用舊規則，240 會被拒絕。

### 2.2 方法

- 測試圖：`synth_1600x1537`（合成）、`sakura_2400x1606`（`01_sakura_portrait` 放大），非正方形且不對齊 tile，有多個內部與邊緣 tile。
- 模型：v3 noise3、noise2_scale2x（az 模型），DML，整張圖走 `src/core/inference` 的切塊與融合。
- tile 256、400 用原版 `tile_runner`；240、384 用 `tile_runner_anytile`，它只把 tile 檢查放寬成 `T >= 64 且 T % 16 == 0`，`src/` 未修改。
- 參考：`scripts/tiled_ref.py`，torch 2.14.1+cpu，走 nunif 自己的 `tiled_render`，載入後移除 tile validator。對照：tile 256 與 nunif CLI 的輸出逐像素相同（s01_scene、noise3 與 noise2_scale2x）。

### 2.4 tile 選項

- 400 在 v3 上不會產生錯誤輸出，所以這不是修 bug。
- **仍建議改成 160／256／352／448**：這四個在 v3 與舊 4× 圖的上游規則下都合法，P1 重做已驗證；400 違反 v3 上游規則，上游自己也不會用它（降到 384）。保留 400 就要在程式裡放寬上游規則，換來的只是省一次設定遷移。
- 已存的 400 要遷移，建議對應到 352；這是 P2 的工作，也要請你確認。
- `T % 16 != 0` 的尺寸（例如 408）未執行，程式也不該接受。

## 4. 流程

**串接，不合併**，理由：

- 兩項修正對應兩個獨立的 DML 問題，日後可分別移除。
- `rewrite_pad.py` 的雜湊不變（`193fba27…`），它已驗證過的輸出也不必重驗。
- `rawpad` 診斷需要單獨跑第二步。

順序寫死在 `fetch-models.ps1`；manifest 列出其他步驟就拒絕執行。第二步會 import 第一步的 `Graph`，兩支腳本都有雜湊檢查。

| 檢查 | 時機 |
|---|---|
| 來源 zip、`source_sha256` | 轉換前 |
| 兩支腳本的 `script_sha256` | 轉換前 |
| `pad_sha256` | rewrite_pad 之後 |
| `sha256` | fix_reshape_allowzero 之後 |

自測：`test_fix_reshape_allowzero.py` 6／6（清除、靜態無 `-1`、無屬性、`allowzero=0`、動態保留、0 與 -1 並存要 STOP），`test_rewrite_pad.py` 全部通過。

| 模型 | `allowzero` 節點 | 改成 0 | 動態保留 | 結果 |
|---|---|---|---|---|
| 舊 20250502（14 個） | 0 | 0 | 0 | 與 manifest 逐位元組相同 |
