## 4. 已知問題與注意事項

- **887A0020**（DRIVER_INTERNAL_ERROR）只在診斷模式出現過，一般執行沒有遇過。
- **tile 640 會讓 GTX 1060 6GB 的裝置停止回應**（4×），所以不提供 640 以上。
- **tile 大小會影響輸出**：上游 swin_unet 本身的特性，例如 4× 合成圖 t160 對 t256 為 35.8 dB。降到 160 的項目會在清單與完成摘要中標示。
- **編碼中取消要等編碼做完**：4× WebP 無損最多約 6 s；不會留下輸出檔或 `.tmp`。
- **4× 透明圖約用 2.1 GB** private memory（RGB 與 alpha 兩個 Session 並存）；建議 8 GB RAM。
- DML 用過之後約有 280 MiB 的固定殘留，不會隨張數增加（P3 實測 49 張）；CPU 沒有這種殘留。
- 每批第一張會慢 4–6 s（建立 Session、檢查雜湊），ETA 另外用 `#cold` 學習。
- 只在 Windows 11 25H2＋GTX 1060 6GB 上實測過；Windows 10、AMD／Intel GPU、多 GPU（固定使用預設轉接器）都沒有測。
- 2026-11-03 P3 截圖時，曾用舊的遷移程式改動過使用者實際的設定（`model/tileSize` 與 `progress/` 已遺失，無法還原）；P4 的遷移已改成不破壞。
- 真實測試圖只放在 `tools/winml-probe/_work/test-images`，不得提交。

### v3 契約

來源：nunif `0d3d92c` 的 `waifu2x/models/swin_unet_v3.py`（`tile_size_validator` 第 224–225 行、`SwinUNet1xV3` 第 229–236 行、`SwinUNet2xV3` 第 256–263 行）。預設值來自 `nunif/models/model.py:71`，值域來自 `nunif/utils/pil_io.py:223`，alpha 來自 `waifu2x/utils.py:261` 起的 `convert`。P1 重做已用推論驗證輸出邊長與 tile 規則，整張圖對 nunif CLI 最多差 1 LSB；alpha 流程未執行。

| 倍率 s | offset（輸出像素） | blend_size（輸出像素） | input_offset | input_blend | 輸出邊長 |
|---|---|---|---|---|---|
| 1 | 8 | 4 | 8 | 4 | T − 16 |
| 2 | 16 | 8 | 8 | 4 | 2T − 32 |

- **沒有 4×**：只有 1×／2× 權重（noise0–3、noise0–3_scale2x、scale2x）。`SwinUNet4xV3` 類別存在，但修補包沒有權重，匯出腳本也沒有路徑。
- **合法 tile**：`T >= 64 且 T % 32 == 0`（64、96、128、160、192、224、256、…）。舊模型是 `T > 16 且 (T − 16) % 48 == 0`。兩者都合法的是 64、160、256、352、448、…（每 96 一個）。
- **手動 tile 400 違反 v3 上游規則**（400 % 32 = 16），nunif 自己會降到 384。`ModelContract::isValidTile`、`core::isOfferedTile` 目前都是單一規則，採用 v3 時要改成依模型判斷。v3 圖的結構限制其實只有 `T % 16 == 0`，所以 400、240 切塊後輸出仍與 PyTorch 一致（P1 收尾報告 §2）；ONNX 不會擋非法 tile，只能靠程式檢查。
- **輸入**：`x`，FLOAT，`[batch, 3, H, W]`，RGB，值域 0–1（8 位元影像除以 255）。**輸出**：`y`，FLOAT，同樣的 channel 順序，圖內 Clip 到 0–1。名稱與舊模型相同。
- **上游預設**：tile 256、batch 4。
- **alpha**：做法與舊模型相同，2× 用同資料夾的 `scale2x`，1× 不處理 alpha。v3 沒有 4× 的 scale 模型。
- **切 tile、融合的公式**沿用 P0-P1 報告 §8.2–8.3，P1 重做已與上游輸出比對確認。

### 匯出模型的已知事項

P0 重做的完整結果見 `docs/v2.0-P0重做報告.md`。

- **swin_unet/art 重新匯出後也是 dynamo**，不是舊匯出器。原因：`waifu2x/export_onnx.py:22` 的 `dynamo=False` 讓 `nunif/models/model.py:90` 走 `else` 分支，但第 115 行的 `torch.onnx.export(...)` 根本沒有傳 `dynamo`，於是用了 torch 的預設值 `True`。權重與舊 zip 逐位元相同，但圖完全不同（opset 17 → 20、節點 7790 → 1702、新增 `Gelu`），P2–P5 的結果不能直接沿用。v3 則是明確傳 `dynamo=True`（`export_onnx.py:124-132`），不受 torch 預設值影響。
- **dynamo 圖在 DML 上要處理 `Reshape allowzero=1`**：DML EP 的 `allowZero` 分支不解析 `-1`，Run 會失敗，1.24.4 與 1.28.3 都一樣。`fix_reshape_allowzero.py` 把靜態 shape 含 `-1` 且不含 `0` 的節點改成 `allowzero=0`，CPU 輸出逐位元相同，已納入正式流程。
- **art 4× 新圖的 14 個 `Gelu` 全在 CPU**，CPU 節點 691 個；v3 的 `IsNaN`、`Resize`、`Pad edge` 都在 DML。
- **每個 v3 主模型都有 1 個負數 Pad**（1×：−8；2×：−16），另有 16 個 `edge` Pad；`rewrite_pad.py` 已能處理，23 個模型都通過。
- **v3 沒有發現寫死的 tile 尺寸**：P1 重做在 160、240、256、352、400、448 都能執行。
- 重新匯出後所有檔案的雜湊都改變了；是否能重現（同環境重跑雜湊相同）未執行。

## 5. 工作規則

- 不動標籤、Release、`main`，也不推送遠端（除非使用者明確要求）；只在 `v2.0-prep` 上提交。
- commit 不加 Co-Authored-By。
- 手動啟動 app 一律用 `--settings-dir <暫存資料夾>`；截圖走 tst_ui 的 `ARX_UI_SNAPSHOT`（測試本身就用隔離的設定）。
- 大型檔案與中間產物放在 `tools/winml-probe/_work/`（不進 git），例如：P3 的驗證輸出 `_work/p3/`、P2 的參考輸出 `_work/p2/`、2.4.89 的 DLL `_work/build-2.4.89/`。測試用的 staging 複本也建在 `_work/` 底下，測完刪除；不在 `build/` 裡替換 DLL。
- 建置：`build.ps1`（VS 2026、MSVC 14.51、`release` preset）；測試：`ctest --preset release`；`tests/arx_verify` 是用真實引擎做實機驗證的工具（不在 ctest 中）。
- 未執行的項目寫「未執行」；涉及程式庫用法時先查 Context7，報告最後列出查過的文件。

依據：nunif 作者 2026-11-03 的回覆（`docs/licenses/inquiries.md` §1）。這裡的 P0／P1 是指換代後重做，不是 §1 中舊模型已通過的階段。

**匯出已完成**（2026-11-03 UTC，完整指令，59 分鐘，exit 0），結果見 `docs/v2.0-P0重做報告.md`。程式與 manifest 尚未切換。

**模型來源的完整寫法**：nunif `0d3d92c` + torch 2.14.1+cpu + onnx 1.23.2 + onnxscript 0.7.2。只寫 nunif commit 不足以描述這批模型：

- torch ≥ 2.9 預設 dynamo，2.11 起移除 `fallback`（`torch/onnx/__init__.py` docstring 的 `versionchanged`）。
- nunif 沒有指定 `dynamo`（swin_unet 路徑）和 `opset_version`（所有路徑），這兩項都取自 torch 的預設值；目前的預設 opset 是 20。
- 換 torch 版本重新匯出會得到不同的圖，雜湊、節點、opset 都可能改變，要重做 P0 檢查與 P1。例如 torch < 2.9 時，swin_unet/art 會走 TorchScript，v3 仍是 dynamo。這是依原始碼推論，沒有實際用其他 torch 版本匯出。
- nunif `requirements-torch.txt` 固定 torch 2.14.1，但 `requirements-dev.txt` 的 `onnx`、`onnxscript` 沒有固定版本，所以要自行記錄。

本次環境（全部在 `tools/winml-probe/_work/` 底下，已被忽略，不提交二進位檔）：

流程（在 nunif 根目錄）：

1. 確認 commit；要更新到新版時先比對差異。
2. 建隔離 venv，安裝 PyTorch CPU 版（torchvision ≥ 0.15）、`onnx`、`onnxscript`，記錄實際版本。
3. 執行 `python -m waifu2x.download_models`，確認 `waifu2x/pretrained_models/swin_unet_v3/art` 存在。
4. 執行 `python -m waifu2x.export_onnx -i ./waifu2x/pretrained_models -o waifu2x/onnx_models`。

注意：

- 不要沿用 `_work/nunif-home`：那裡的 20260816 標記檔是 P2 刻意放的空殼，下載腳本看到後會略過 v3，`swin_unet_v3/art` 就不會出現。`NUNIF_HOME` 不設定時，模型會放在倉庫內，正好是上面 `-i` 的路徑；如果改用新的 `NUNIF_HOME`，`-i` 也要跟著改。
- 匯出腳本沒有選擇模型的參數，會把 cunet、photo、art_scan 也全部匯出（共 72 個檔案，CPU 約 1 小時），只取需要的檔案即可。
- 重新匯出時固定上面的版本；要換版本就當成新來源處理。
- 切換來源後要跟著改的檔案：`models/manifest.json`、`tools/fetch-models.ps1`、`tools/package.ps1`（來源字串）、`tools/winml-probe/fetch-deps.ps1`、`tools/collect-licenses.ps1`（nunif `LICENSE`／`NOTICE` 目前固定在 `31c0137`，要改成匯出用的 commit）、`licenses/README.md`。
