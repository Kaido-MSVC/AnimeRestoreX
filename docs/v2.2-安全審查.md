## 1. 摘要

未確認高嚴重度問題、任意程式碼執行或輸入檔遭修改／刪除的圖片攻擊路徑。優先處理下列三項；前兩項都是不受信任圖片繞過既有資源限制的實際入口。

1. **中：PNG iCCP 解壓縮沒有真正的輸出上限。** `qUncompress()` 會自行增加緩衝區，32 MiB 的限制實際只限制壓縮資料／初始提示值；小圖片仍能帶入大幅膨脹的資料，拖入清單便可能大量占用記憶體。
2. **中：PNG IHDR 依未驗證的 chunk 長度配置記憶體。** 在確認長度應為 13 bytes 之前，最多可要求約 2 GiB；即使檔案截斷也會先配置，而且主處理在圖片解碼與像素檢查之前就會走到這裡。
3. **低：保留 EXIF 時，移除 IFD1 不保證清除縮圖位元組。** 對損壞、重疊或多 strip 的結構，程式可能只斷開指標，仍把原縮圖／殘留資料複製到輸出。此項只發生於開啟「保留 EXIF」時，預設關閉不受影響。

第三方確有較新的安全修補，但不能把套件版本命中直接當成本程式漏洞：libpng 1.6.58 的 CVE-2026-46675 要求不同於 Qt 正常讀取流程的呼叫順序；zlib 1.4 修補的幾個危險 API，也未在本次核對的圖片路徑中發現使用。詳細適用性與升級建議見第 3 節。

### 2.1 S-01 的第三方行為證據

本機 `qtbase-everywhere-src-6.12.0.zip` 內的 `src/corelib/text/qbytearray.cpp:703–713` 明載提示不足時會擴大緩衝區，64 位元甚至可產生超過 4 GiB 的結果；實作見 `729–763`。這不是猜測 Qt API 的行為，也不是 zlib CVE。官方文件有相同行為說明：[qUncompress](https://doc.qt.io/qt-6/qbytearray.html#qUncompress)。

此外，預覽 `src/ui/PreviewPane.cpp:337–340` 與縮圖 `src/ui/MainWindow.cpp:393–400` 雖然在 `read()` 前查像素上限，但 `OrientedReader` 建構子已為 PNG／WebP 呼叫 `metadata::read()`。因此像素上限無法取代中繼資料的配置與解壓上限。

### 2.2 後續有限驗證建議（本次未執行）

- S-01：以正常小圖配合略高於 32 MiB 的可壓縮資料，在隔離程序中驗證「超限略過 ICC、正常像素仍輸出」；不必把主機記憶體耗盡。
- S-02：以截斷 IHDR 與錯誤長度測試，觀察配置要求是否在讀取前遭拒絕；不必真的配置 2 GiB。
- S-03：以單 strip、多 strip、錯誤 IFD1 與重疊資料各一例，檢查輸出 EXIF 的原始 bytes；不只查 IFD1 指標為零。

## 4. 已檢查沒問題的範圍與適用限制

下列「未發現問題」限定目前靜態審查及所述邊界，不代表任意損壞檔案都經過實測。

### 4.1 JPEG／PNG／WebP 容器解析與寫出

- **JPEG APP1／APP2／SOF：未發現可達越界存取。** `ImageMetadata.cpp:105–163` 在讀取前檢查 marker 與 16 位元 segment 長度，SOF 存取要求至少 6 bytes，ICC 分片要求 14 bytes，檢查序號、分片總數與重複分片。256 個可能序號與 segment 長度讓暫存量有界；不會因宣告巨大 TIFF count 就先配置該資料量。
- **PNG：除 S-01／S-02 外，eXIf 有 4 MiB 上限，iCCP 壓縮內容有 32 MiB 上限，chunk 長度先擴成 qint64 再加 CRC。** 見 `ImageMetadata.cpp:57–103`。讀取端略過 CRC、不驗證輸入 CRC，屬容忍損壞資料，不能宣稱完成容器有效性驗證；不據此單獨推論記憶體漏洞。程式自己的 metadata reader **沒有解析 PLTE**，只用 IHDR 判斷灰階，調色盤與像素解碼交給 Qt／libpng。
- **WebP：未發現 32 位元 chunk 長度加一溢位。** `ImageMetadata.cpp:166–199` 先轉 qint64 才計算偶數填補；EXIF／ICCP 大小受限制，短讀會退出。讀取端未把 RIFF 宣告長度當成終點，可能讀到其後附加 chunk；會影響中繼資料採用範圍，但沒有由此找到主程式越界或檔案寫入攻擊，未另列漏洞。
- **PNG 寫出：未發現 CRC 計算範圍或 chunk 長度錯誤。** `ImageMetadata.cpp:320–361,487–502` 以 type＋data 計算 CRC，不含 length；在固定 13-byte IHDR 後插入資料。
- **JPEG 寫出：未發現 APP 長度截斷的產品路徑。** `ImageMetadata.cpp:364–394` 與 `ProcessJob.cpp:521` 先限制 EXIF，ICC 分片上限為 255，每片連標頭不超過 65535；不把整個大 ICC 直接轉成 quint16。
- **WebP 寫出：未發現產品可達的 RIFF 大小截斷或越界寫入。** `ImageMetadata.cpp:397–482` 驗證編碼後 RIFF 大小、chunk 邊界，VP8X 原有資料須為 10 bytes；新建時先配置 12 bytes，寫入 width／height 後截為 10；各 chunk 有偶數填補，最後填 `out.size() - 8`。目前輸出像素與中繼資料上限下不會接近 4 GiB。此函式接收的是 Qt 新編碼結果，不是直接改寫任意來源 RIFF；S-01 應先補正，不能把未受限制的解壓 ICC 當作永久安全前提。

### 4.2 TIFF／EXIF

- **已檢查一般越界與乘法：未發現越界讀寫。** `ImageMetadata.cpp:213,257–291` 用 `n <= size - off` 驗證範圍；IFD entry 數不超過 4096；`count` 是 quint32、型別大小最大 8，以 qint64 相乘，最大約 34 GiB，未達 qint64 溢位，再檢查實際區塊範圍。Windows x64 的 qsizetype 為 64 位元，quint32 偏移轉換不截斷。
- **沒有遞迴走任意 IFD 圖的迴圈。** `ImageMetadata.cpp:596–618` 僅走固定的 IFD0、Exif、GPS、Interop，對這幾個指標用 `seen` 拒絕回指。`exifOrientation():564–579` 只查 IFD0。未發現循環參照讓本解析器無限遞迴。
- **限制：這不是完整 TIFF sanitizer。** 未知 type 的值範圍不驗證（`:246`）；sub-IFD 的 next 指標未遞迴驗證；保留區之間沒有全面禁止重疊。這不會自動構成目前程式的越界，但不能承諾所有不合法 EXIF 都被略過。IFD1 的失敗與殘留問題列 S-03；其他未找到具體安全後果的容忍行為不灌入發現數。
- **方向與尺寸寫入：未發現越界。** `ImageMetadata.cpp:620–638` 只修改已驗過的 entry inline value，SHORT 放不下輸出尺寸時改 LONG；不額外插入未配置空間。
- **一般格式錯誤會略過 EXIF 並繼續輸出。** `ProcessJob.cpp:514–529` 接住 `prepareExif` 的 expected 錯誤；`ImageEncoder.cpp:109–117` 嵌入失敗退回純編碼資料。但配置失敗不全在這個錯誤模型內，S-01／S-02 不能被「格式錯誤會略過」的說法涵蓋。

### 4.3 圖片解碼、Tile、TTA、顆粒與顯示路徑

- **主要像素上限有效。** `ImageLimits.h:13–14` 是輸入 **4.5M**、輸出 **75M**。`ImageLoader.cpp:112–129` 在已知標頭尺寸時先檢查，讀完再檢查實際尺寸；`ProcessJob.cpp:371–373,399` 再檢查輸出並把上限傳入核心。4× 實際最多 72M，因為 4.5M × 16 = 72M。
- **尺寸乘法未發現溢位。** `ImageLimits.cpp:17–48` 的像素相乘先轉 qint64；輸入先通過 4.5M 限制後才進一步乘倍率。`TileProcessor.cpp:24–27,134–138,454–461` 有 mulOk、輸出邊長 int 範圍與輸出像素上限。合法倍率 1／2／4、tile 160／256／352／448、manifest offset／blend 上限共同限制其餘 int 算式，不能用任意函式參數值推論產品可達溢位。
- **TTA 沒有同時保留八張結果。** `TileProcessor.cpp:452–506,551–573` 是一份 3-float accumulator，加上單次 render 的 sum／weight；記憶體預算乘 28 bytes／輸出像素，主要配置捕捉 bad_alloc。75M 上限不是整個程序的 RAM 上限，正常大圖仍可使用數 GiB；與交接的建議 16 GB 一致，不因正常較高用量另列漏洞。
- **顆粒沒有配置整張 float 雜訊圖。** `TileProcessor.cpp:74–85,252–261,510–518` 逐像素計算，額外配置主要是 X 對應表與列索引；NaN／無限大強度在設定與工作選項驗證被排除，量化也會把 NaN 轉為 0（`:30–36`）。
- **預覽／縮圖的像素解碼保護已存在。** `PreviewPane.cpp:323–357` 對原圖 4.5M、結果 75M 檢查，未知尺寸不解碼；`MainWindow.cpp:393–402` 縮圖同樣檢查 4.5M。PNG 的 `setScaledSize()` 不保證降低解碼峰值，現有程式沒有只靠縮放保護。這也符合 [Qt QImageReader 文件](https://doc.qt.io/qt-6/qimagereader.html#setScaledSize)。**中繼資料較早執行的例外見 S-01／S-02。**
- **尚未證明所有 OOM 都可恢復。** alpha 邊界暫存、filter、grain 對應表／列索引等配置不全在 bad_alloc 捕捉內（`TileProcessor.cpp:168,281–283,306–307,253,518`）。需要主機已低記憶體或其他配置失敗條件，未實測具體當機，故不另列成可由正常小圖必然觸發的安全漏洞；下一次配置錯誤處理維護可一併補齊，不做真實耗盡主機的測試。

### 4.4 DLL 與 Qt 外掛

- **ORT delay-load 與三顆 runtime 固定路徑：已檢查，未發現圖片可利用的 CWD／PATH 搜尋。** `src/CMakeLists.txt:17–30` 使用手動 ORT API 初始化與 `/DELAYLOAD:onnxruntime.dll`。`OrtTileEngine.cpp:58–90` 設預設搜尋目錄為 application＋System32，再以 exe 目錄絕對路徑及 `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32` 依序載入 DirectML、ORT、WinML；檢查模組實際位置、同名數量與 ORT 精確版本。
- **此保護不是簽章或防竄改驗證。** DLL 載入時會先執行 DllMain，之後的路徑／版本檢查無法撤銷它；exe 同目錄可寫的攻擊者本來也能替換 exe。套件雜湊在封裝時核對（`package.ps1:267–276`），執行時沒有逐顆驗證 SHA-256。此威脅需要控制程式目錄，並非只控制拖入的圖片，因此未另列 DLL 劫持發現。
- **Qt 外掛未被程式強制鎖在唯一目錄。** `main.cpp:22` 已建立 QApplication，runtime 限制到 `:74` 才初始化；沒有 `setLibraryPaths()` 或隨封裝提供的 qt.conf。Qt 正常的外掛路徑規則仍適用，包含環境設定；[官方部署文件](https://doc.qt.io/qt-6/deployment-plugins.html)。封裝只允許 `platforms/qwindows.dll`、`imageformats/qjpeg.dll`、`qwebp.dll`（`package.ps1:221–225`），但「封裝 allowlist」不等同執行時外掛沙箱。未找到圖片能變更環境或外掛搜尋路徑的途徑，不把需要先控制啟動環境的條件列成圖片漏洞。
- **範圍限制：** Windows 在 main 之前載入 Qt／CRT 的標準依賴，故 runtime 函式不能宣稱保護全部啟動階段；保留完整官方 zip、不把來源圖片中的 DLL／外掛搬入程式資料夾，符合這個小型工具的合理邊界。

### 4.5 輸出檔與輸入檔保護

- **未發現來源檔名造成路徑穿越。** `OutputNaming.cpp:10–26` 取 `completeBaseName()` 後加 `_倍率x`，副檔名由固定 enum 對照（`ImageEncoder.cpp:22–29`），不把來源絕對路徑／目錄字串拼進輸出檔名。輸出目錄是使用者明確選擇的目錄。
- **不覆寫現有輸出或同名來源。** `OutputNaming.cpp:29–49` 已存在則依序加 `(n)`，rename 不取代目的檔；最多試 10000 次。檔名增加 `_1x` 等後不會直接等於其來源；即使另一個輸入恰好同名也會被存在檢查避開。
- **暫存檔不截斷既有檔。** `ProcessJob.cpp:537–541` 用 `NewOnly` 建立，RAII 清理只在成功建立後安裝；失敗、取消或提交失敗時關檔並刪除這份暫存，成功才 release（`:34–49,552–568`）。另有寫入／flush／關檔錯誤檢查。沒有找到對 `sourcePath` 的 WriteOnly、remove、rename 或覆寫流程。
- **保留名稱／過長路徑：** Windows 一般來源檔已受檔案系統命名規則限制，加上倍率後也避免直接產生 `CON.png` 等常見裝置名。來源檔名接近長度上限時，加字尾／暫存名可能無法建立；現有程式會回報失敗，不會改名截短或退回寫入來源。沒有把這種使用失敗當成安全漏洞。
- **不能承諾對敵對可寫目錄「任何情況」都保全來源。** 若另一個程序能在開檔與 rename／remove 之間移動檔案、替換目錄或重解析點，目前程式未以控制代碼鎖定整個輸出名稱空間。這需要檔案系統寫入能力，未找到僅靠圖片內容的觸發方法，依本次威脅模型不列競態發現；也未進行破壞性取消或競態測試。程序被強制終止時 RAII 不執行，可能留下 `.tmp`，不是刪除來源。

### 4.7 EXIF 隱私、diagnostics 與網路

## 5. 建議修正順序

1. **下次分享新版前先修 S-01／S-02。** 它們直接接受不受信任圖片、位於像素保護之前，不需要攻擊者先取得電腦上的寫入權限。先實作 bounded 解壓與固定 IHDR 長度驗證，再做第 2.2 節的小型回歸；無須真實耗盡 RAM 或全面重跑推論品質測試。
2. **同次順手修 S-03，或至少在下一版修。** 解析不明／無法可靠清除縮圖時略過整段 EXIF，是符合既定決策的最小修改；不用全面重寫 TIFF。保留 EXIF 預設關閉，故優先度低於前兩項。
3. **Qt 與內附 libpng／zlib 安排維護更新。** 目標是官方修補版，以及確實包含 libpng ≥ 1.6.59、zlib ≥ 1.4 的組合；確認實際內附版本後再決定是否需要重建 Qt。這些公告目前未建立本程式可達攻擊路徑，不因公告名稱就阻擋離線少量分享，也不因「升了 Qt」就略過 S-01。
4. **可等下一版：** 對可恢復配置失敗加一致的工作邊界錯誤處理、manifest 浮點轉 int 前的範圍驗證、視需求縮小 Qt 外掛路徑與提供 log 路徑遮蔽。模型 TOCTOU 只有在加入外部模型／共用可寫目錄等新信任邊界時，才有必要提高修正優先度。

### zlib

- 版本：**zlib 1.4**（2026-11-05，當日最新穩定版）。不放進 repo，照 `tools/fetch-*.ps1` 的模式由新的 `tools/fetch-zlib.ps1` 下載到 `third_party/zlib/1.4`（git 忽略），SHA-256 固定為 `02dd1597…6ad584`。固定前核對過：GitHub Release 附件與 zlib.net 的檔案相同；`zlib-1.4.tar.gz.asc` 是 Mark Adler 的有效簽章（金鑰指紋 `5ED4 6A67 21D3 6558 7791 E2AA 783F CD8E 58BC AFBA`，以暫時的 keyring 驗證，沒有動到全域設定）。

### JPEG／WebP 讀取路徑（S-02 順帶檢查）

- JPEG：segment 長度是 16 位元，配置最多 65,533 bytes，而且是先讀到長度欄才配置，沒有「依宣告長度先大量配置」的情況，與審查結論相同，沒有修改。
